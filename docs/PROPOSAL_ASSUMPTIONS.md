# 方案準備：核心假設、適用範圍與升級路徑

日期：2026-11-10。狀態：使用者已接受八項核心假設作為方案準備基線；各對口正式承諾、數值門檻與能力證明仍待確認。所有正式 owner／接受者待指定。公開模式與來源見 RESEARCH_BASELINES.md；本文件是根據那些模式形成的提案假設，不是業界普遍需求的統計結論。

## 要賣出的價值與適用範圍

候選價值：在主要 cluster 不可用時，讓既有使用路徑仍能完成可信的搜尋、閱讀、下載；以可驗證的版本發布與可交接的恢復流程，降低系統端及 consumer 的總負擔。

適用客群：可接受有界資料落後、故障期間主要需要唯讀知識存取、可取得獨立身份／授權能力、能產生可驗證資料副本的系統。未證明覆蓋「多數系統」。不預先承諾移除 Backend/DB、零 consumer 改動、任意規模、零資料損失或即時恢復。

準備者先提出具體可反駁假設與選項，讓對口選擇代價；不等待所有需求才開始，也不把自己的測試當成對口接受。

## 八項核心假設契約

| ID | 建議預設／設計底線 | 理由與服務對口 | 目前狀態／驗證 | 不成立時的影響 |
|---|---|---|---|---|
| H01 | 故障時保住指定唯讀任務；寫入明確不可用，不偷偷累積待回寫狀態 | 限縮到 User 可完成的重要任務，降低 DevOps 合併責任 | 合成讀取範圍內通過；正式任務待裁定 | 若需寫入、交易或雙向同步，重選資料與復原設計 |
| H02 | 正文及媒體可落後但必須有時效上限；顯示成功版本時間、來源時間界線及同步狀態 | User 判斷可信度、Reviewer 定義承諾 | 每日同步僅排程假設，不是 RPO；max age 待裁定 | 秒級／零損失可能需要 CDC、同步複寫與預熱，不當作簡單調頻 |
| H03 | 必要正文、metadata、媒體關聯與 bytes 可在故障前產生可驗證副本；請求不回查故障來源 | DevOps 獨立性、精簡方案的成立前提 | 合成資料包範圍內通過；正式匯出界線未知 | 先補匯出／保留必要 read backend；若大量即時邏輯不可匯出，重新評估精簡 |
| H04 | 一個操作鏈使用完整 release；未驗證新版不 active；失敗保留「仍符合交付政策」的舊版 | User 不混版、Consumer 不自行拼接、DevOps 可恢復 | 本地拒絕故障有證據；M01 發布及多程序待驗證 | 多節點瞬間同版若為必要，需額外協調；完整舊版不等於永遠可交付 |
| H05 | 每次操作依獨立可用的身份／授權政策檢查；未知或失敗拒絕，內容版本不能豁免授權 | 所有對口的安全基礎 | mock 有證據；p09 舊歸屬是已知反例 | 必須另定撤權／移動／刪除時效；離線授權是獨立高影響選案，不算加分選項 |
| H06 | consumer 使用穩定讀取契約；版本協調盡量留在 provider，版本資訊可由 opaque cursor/link 傳遞 | 降低各 client 維護分支與長期負擔 | 合成 Node reader 通過；HTTP／正式 client 未驗證 | 若舊 client 不接受 token/link 或錯誤改變，需要 adapter／保留原 route；不得預設零改動 |
| H07 | 復原包括啟動、身份、路由、依賴與完整使用流程；可先由人依文件啟用 | DevOps 可交接、Reviewer 有明確恢復邊界 | 正常冷啟動通過；正式端到端／切回未知 | 小時級改為秒級通常要 warm/hot、導流及演練；不是只調 timeout |
| H08 | 總負擔用整個生命週期比較，正確性門檻通過後才比較成本 | Reviewer 有採用依據；避免成本轉給 consumer | 正式成本資料缺失，待驗證 | 若自製發布/API 維護抵銷服務節省，保留原元件是合理結論 |

H01–H08 不全是可調假設：不混版、不越權、不以不完整資料冒充成功是設計底線；可接受 age、復原時間、API 差異是需求選擇；匯出、獨立身份能力是待證明的外部前提。不能混為「我們先假設都成立」。

## 避免大改的設計接縫（先定契約，不先造平台）

1. 來源匯出與版本資料契約分開：schema/version、引用集合、來源界線、完整性證據；不把某個 DB schema 直接當 consumer API。
2. 資料準備與發布決策分開：publisher 只讓已驗證 release 可見，保留狀態與可恢復紀錄。初期單寫者，並行發布有需求再擴充。
3. reader 固定 release descriptor：確切 ES index、內容／媒體版本與 schema 相容；一次請求不能因 active 改變而中途換版；跨請求以明確契約承接。
4. consumer API 與內部存放格式分開：可用 adapter 保留外部契約；任何 adapter 都有測試及維護成本，不能聲稱任意相容。
5. 授權／新鮮度政策為明確邊界：每次授權照常執行；可服務 age、撤銷訊號與資料版本分開。不先建立通用 policy engine。
6. readiness 與發布時間線為共同觀測：顯示 active/candidate、驗證拒絕理由、資料 age、必要依賴；保留能讓非作者判讀的 runbook。

這些邊界可先實作為同一程式的模組，不代表新增六個服務。目的是局部替換與獨立驗證；抽象本身也要有成本上限。

## 需求變化分級：不把所有變化稱為加分

| 變化 | 候選調整 | 必須重驗／可能跨級的條件 |
|---|---|---|
| 每日同步改每幾小時 | 調整排程與告警 | 匯出／傳輸／驗證必須趕得上；來源負荷增加可能需增量 |
| 多保留幾版或延長操作鏈 | 保留政策及 cursor 壽命 | 磁碟、敏感資料期限、在途連結與 GC；不可只調數字 |
| API 欄位／錯誤格式差異 | provider adapter | 若缺資料或需要原服務即時計算，升級為依賴變更 |
| 大附件與中斷續傳 | 串流／Range 及版本固定讀取 | 授權、hash 驗證時機、記憶體、既有 client 行為需測 |
| 更短恢復時間 | warm standby、自動啟動／導流 | 成本與故障偵測／身份／跨區依賴；秒級是可能的架構變更 |
| 更嚴格撤權時效 | 更快關聯更新、拒絕資料或暫停過舊副本 | 獨立更新通道是否仍可用；無法保證時不得冒充只是加分 |
| 多 consumer／更多流量 | 擴 API 副本、快取、併發預算 | ES／MinIO／ReBAC 瓶頸與跨副本版本；未做容量保證 |
| DR 要寫入／多地同時修改 | 重開需求與選案 | 雙向同步、衝突、切回資料合併，超出唯讀基線 |
| 不允許任何內容落後／來源永遠不可凍結 | 重開來源及複寫設計 | 不是定時 release 方案的簡單升級 |

## 最少但關鍵的需求談法

用具體代價題代替泛問「你有什麼需求」。以下無預設答案，先作對口討論腳本：

- User／產品：昨天的完整 runbook 與附件，是否比今天一半資料有用？哪些內容過期就不應提供？（決定 H02/H04）
- 產品／授權：Page 搬到受限 Space 後，多久內必須阻止舊版存取？授權服務失聯時是否接受拒絕服務？（決定 H05；既有反例可示範）
- Consumer：可接受改設定、跟隨 provider link、加一個 header，還是連錯誤碼也必須完全不變？選一個真實 client 重播。（決定 H06）
- DevOps：事故後可接受哪個人執行哪些動作？不在場時誰能替代？先以非作者照 runbook 操作驗證。（決定 H07）
- Reviewer：優先購買更短中斷、更少平時成本，還是更少 client 改動？同一承諾下比較，額外承諾列出價格／責任。（決定 H08）

## 三條並行工作線與投資關卡

需求線：每輪只確認一兩個最可能使架構翻盤的假設；回覆紀錄為接受／拒絕／需證據，不假裝未知已解。
可行性線：在已標明的假設內實驗，結果必須能推翻或支持選案；例：M01 僅證明已封存合成版本的發布，不跨越正式來源與權限未知。
提案線：持續展示任務、代價、證據與下一筆投入，不等所有技術完成才談採用，也不把待驗證能力包裝成完成。

- G0 值得試：重要唯讀任務有潛在價值，無已知不可接受的前提；合成實驗可先走。
- G1 值得整合：版本發布故障可控制；代表性 HTTP client 可完成流程；沒有未處理混版。仍不是正式試行批准。
- G2 值得試行：正式資料／授權／client 過關、非作者可恢復、age 與剩餘風險有具名接受者。
- G3 值得常態採用：同承諾的總負擔有資料、責任落定、演練與切回完成。通過門檻後再安排加分項。

目前只有特定 synthetic 與冷啟動證據；未跨 G1/G2/G3。此分級是提案工作法，不取代 VERIFICATION_PLAN 的證據狀態。

## 可直接使用的提案開場（假設式價值主張）

「對可以接受有界資料落後、但事故期間仍需要知識讀取的團隊，我們正在驗證一套唯讀備援：保留完整可用版本，盡量沿用 consumer 的既有流程，讓值班人員有可交接的恢復方式。合成讀取與正常啟動已有證據；發布一致性、正式相容性與總成本會分階段驗證。若需要故障期間寫入、零資料落後或離線授權，我們會明確提出不同方案及代價。」

近期要爭取的是代表性任務／client、產品與授權裁定窗口、DevOps 演練參與及有停止條件的驗證投入；不是要求先批准最終架構。提出價值時同頁顯示前提、證據、未解風險、投入與退出條件。

## 2026-11-10 採用主軸修正：Reviewer 支持與跨團隊價值

使用者補充：主要推進壓力來自 Reviewer，可能包含非技術的美國廠區管理者。提案須使其理解營運價值並願意協調 consumer、資源提供者與其他 DevOps。方案的主判準是各 stakeholder 的可感知價值能支持其投入；Elasticsearch 結果一致只是特定任務／相容性證據，不是方案目的。

需求與推論分開：上述角色與壓力由使用者提供；各角色的具體收益、成本、決策權與接受門檻仍需核對。Reviewer 是否有預算／跨團隊排程權限尚未確認，不能將其自動視為 sponsor。提案要清楚提出需要他協調哪一項決定。

| Stakeholder | 候選價值 | 需揭露的成本／顧慮 | 第一個具體合作請求 |
|---|---|---|---|
| Reviewer／潛在 sponsor | 知道事故時保住哪些工作、剩餘風險與責任；取得可判斷進度的證據 | 預算、協調時間、承諾及風險接受責任 | 確認優先營運情境；指定或協調對口及有界驗證投入 |
| Consumer 團隊 | 自己的使用流程也有復原能力，少臨時改碼與特殊分支 | client 修改、回歸、長期相容與事故支援 | 提供一個代表性流程及不可接受差異，參與契約驗證 |
| 資源提供者 | 用途、容量與責任可預期，不被臨時救火要求綁住 | 運算／儲存／網路成本、配額、資安、支援期限及回收責任 | 提供有上限的測試資源邊界與既有規範，非先承諾正式容量 |
| 其他 DevOps／值班團隊 | 可判讀狀態、有 runbook 與升級路徑，降低事故不確定性 | 新增監控、輪值、升級、演練與交接 | 以非作者身分走一次限定流程，指出不可接手處 |
| 產品 User／業務代表 | 事故期間仍可完成重要任務，知道資料時效與功能限制 | 降級、不含最新資料、操作切換與學習成本 | 選定任務並裁定可接受降級及資料時效 |
| 方案準備／實作團隊 | 明確範圍與決策支持，可交付且能維護 | 開發、研究、整合與未來 ownership | 記錄投入、退出條件與責任，不默默承接全部缺口 |

不能只用組織總收益掩蓋個別團隊淨增加的負擔；也不能保證每一方自然受益。若成本集中在某團隊，應縮小工作、提供共用 adapter／工具、安排預算工時、調整責任或由有權者明確接受，直到合作條件可成立。安全、法規及授權底線不以收益抵銷。

### Reviewer 的一頁決策輸入

1. 營運情境：哪個廠區／團隊在什麼故障下無法完成哪個重要任務；影響尚未量化就明寫未知。
2. 最低服務承諾：故障時保住什麼、資料可多舊、如何知道能用；不先列技術元件。
3. 選項：維持現況／有限唯讀備援／較完整備援，在同承諾或清楚標示不同承諾下比較成本與風險。
4. 證據與缺口：已驗證的使用流程、待驗證的正式整合；測試數字放附件。
5. 本輪需要的協助：指定對口、協調範圍／優先級、提供有界工時或資源；每項有產出與停止條件。
6. 下個決策點：取得哪些證據後擴大、縮小或停止；讓 sponsor 能控制投入。

### 對研究優先順序的影響

每輪先問：這項結果會幫誰做哪個決定、減少誰的負擔、需要誰配合？先證明業務任務足夠及合作成本可接受，再追求未影響任務的結果一致。既有 ES 比對保留為回歸與相容性證據；若排序／score 差異不影響已接受任務，不自動列為阻塞，反之依賴特定分頁／欄位的 consumer 仍必須驗證。

新假設不追溯改寫舊測試結果，不將未經確認的業務價值量化為節省金額／停工損失。下一個管理向產出以候選重要任務＋stakeholder 收益／投入／合作請求為主，技術實驗為其提供證據。

依使用者回報，PM 已確認 readonly、下載、搜尋方向；因此 H01 的網站功能方向已有 PM 確認來源，但正式任務、時效、API 契約與授權政策仍未全數確認。主管期待取得一個核心 consumer owner 的方案確認、核心 DevOps 對現有資源／合理架構方向與共同對外報告的認同、PM 需求確認，以及 FDE 內部平台／技術可行性諮詢。詳細狀態與責任界線見 `STAKEHOLDER_CONFIRMATIONS.md`，不先擴至多家 consumer，不把 FDE 諮詢當成平台 owner 授權。

## 2026-11-10 現況基準修正

現行已有運作中的 Next.js＋MinIO＋Cronjob＋內部 ReBAC DR，欠缺搜尋、consumer API 與完整授權；詳見 `CURRENT_DR_BASELINE.md`。八項假設用於增量補齊，不從零重建。提案價值是沿用既有投資，使網站與核心 consumer 的必要任務在可接受成本下成立。授權缺口與 API／搜尋平行釐清；保留 lab ES 僅為證據，不預設正式 DR 要引入 ES。
