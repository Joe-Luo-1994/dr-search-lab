# 關鍵角色確認表與對外報告準備

日期：2026-11-10。來源：使用者本輪補充。這四個角色是主管視角的方案確認重點；不等同所有角色均已批准。第一輪只聚焦一個核心 consumer owner，不擴展成多家 consumer 需求盤點。人名、會期與正式權限待填。

## 確認範圍與目前狀態

| 角色 | 要取得的資訊與明確結論 | 目前狀態 | 不代表什麼 |
|---|---|---|---|
| PM（代表 DR 網站 user） | readonly、閱讀／下載／搜尋範圍；代表性任務、可接受資料年齡與降級；使用體驗驗收方式 | 使用者回報：readonly、下載、搜尋方向已與 PM 確認；細節待補 | 未確認恢復時間、授權／撤權政策或全部 UI 行為；不把 PM 自動視為資安政策 owner |
| 一個核心 consumer owner | 檢視主案是否支援該 consumer 必要流程，整合／切換成本及維護分工可否接受；列接受條件及阻塞 | 待方案確認 | 不代表所有 consumer 相容，也不只是提供 API 範例；owner 同意方向不等於整合實測已通過 |
| 團隊核心 DevOps | 現有資源／故障域／身份網路依賴能否承接；架構是否為現階段合理方向；剩餘限制能否共同對外說明 | 待方案確認 | 不只是能啟動服務；方向認同不等於正式容量、SLA 或值班責任全部承諾 |
| FDE（公司內技術諮詢） | 用內部平台現況與發展趨勢檢查可行性、技術選型、可重用能力與遺漏依賴；指出前提、替代路徑及應找的 owner | 待諮詢／驗證 | 不預設具核准權或能承諾 DNS、資源／平台能力；建議仍須由實際 owner 及測試核對 |

## 合作策略：內部 v1 → 外部挑戰 → 策略 v2

使用者澄清：團隊 DevOps 實際管理現行非 DR Infra，熟悉架構與限制。方案準備者提供他們較缺的應用／資料側可行性探索，尤其是在必須存在的 web server 上，除了另起完整 Infra，還能承擔哪些讀取、資料組裝與搜尋能力。討論不以 ES 入門介紹為主。

現況基準以 `CURRENT_DR_BASELINE.md` 為準：已有運行中精簡 DR，內部討論集中在增量搜尋／API／授權；不從零選全套架構。

1. **內部共擬 v1**：DevOps 提供現行拓樸、資源、故障域、營運與權限限制；準備者帶候選責任切分、合成證據、公開先例與待驗證代價。共同找出現階段認為可行的主案與備案，記下前提及待詢問問題。內部認同尚未取得，不以本文件代替。
2. **攜 v1 請教 FDE 與一個核心 consumer owner**：FDE 挑戰內部平台、依賴、選型與切換假設；consumer 挑戰任務支援、契約與整合成本。兩者可並行；帶具體方案徵詢反例，初次諮詢不要求對方批准實作承諾。
3. **形成 v2**：彙整問題，區分必須修正、可接受差異、需實驗、需需求裁定；與 DevOps 修訂架構、責任與實驗優先序，必要時由 PM 補裁定使用需求。對外說明 v1→v2 為何改變、哪些已確認、哪些尚待驗證。

v1 的最低內容：PM 已確認 readonly／下載／搜尋、現況與故障依賴圖、web server／外部元件責任、完整棧對照、證據／限制、各方工作量與待確認清單。不必等所有實驗完成才詢問 FDE／consumer；小實驗只優先回答會改變 v1 選擇的問題。兩版皆非正式上線批准。

## 每場會議的決定題

### 核心 consumer owner

- 用一條代表性使用流程重播：這個方案能否支撐必要任務？哪個差異會使它無法採用？
- endpoint／身份、必要欄位、分頁與錯誤、下載等，哪些既有契約必須保留？
- 需要改哪些地方、由誰維護？在這個範圍內是否同意推進，接受條件及阻塞是什麼？

### 團隊核心 DevOps

- 先借用既有現況知識，不重做 Infra 入門介紹。共同核對 web server 承接讀取邏輯後的部署、資源競爭、故障影響及新增維護責任；不預設必須將所有元件塞在同一程序／主機。
- 現有資源、預算及權限下，主案依賴是否可取得？故障時哪些依賴會一起消失？
- 發布、啟用、監控、回退、清理與切回是否有可接手路徑？不合理的維運負擔在哪裡？
- 是否認同這是現階段值得驗證的架構方向？完成哪些確認後，可以一起對外報告？

### PM

- readonly、下載、搜尋已確認；選一個最有代表性的網站使用任務，定義完成結果。
- 資料時間、不可用／無權限／同步落後訊息與功能降級怎麼呈現？哪些差異不能接受？
- 哪些時效／權限問題需要其他有權對口一起裁定？PM 功能認可不代替授權政策裁定。

### FDE

- 公司內是否已有可重用的流量切換、身份、物件複寫、可觀測性或 DR 平台能力？哪些是現行可用、哪些只是規劃？
- 若 DNS 不由本團隊控制，應採哪種可行切換路徑？實際負責者／權限／申請或故障操作流程為何？
- 候選自動切換由誰偵測故障、誰執行、如何避免誤切與反覆切換、如何回切？DNS cache／TTL、client cache、既有連線、憑證與登入要如何納入？這些是問題清單，不是本案已知能力。
- 技術選型是否符合內部支援、維護、授權與發展方向？有沒有更省整合／維運工作的既有方式？
- 結論應為可行前提、需補驗證、建議找的 owner／替代方案；留下來源和適用版本，不把意見當成實測。

「DNS 不在我們手上」是使用者提出的諮詢例子；目前尚未完成實際 owner／控制權確認，不記為已查證事實。自動切換也尚非 PM 已確認的必備承諾。

## 確認紀錄格式與對外報告出口

每次記錄：角色／具名代表、日期、方案版本、已確認範圍、附帶條件、不同意／未決項、證據或會議紀錄、下一行動／owner／檢查點。歷史意見保留。會議結論可用同意方向／有條件同意／不同意／未回覆；驗證狀態仍依 VERIFICATION_PLAN 分開記錄。

正式準備共同對外說明時，要能展示：

- PM 已確認的功能範圍及待裁定細節。
- 一個核心 consumer owner 對方案的結論與條件。
- 核心 DevOps 對資源限制、架構合理性及共同報告的結論。
- FDE 已諮詢結果、未解前提與涉及的平台 owner；若尚未取得，對外標示待諮詢，不能宣稱完整技術把關。
- 四方結論是否互相衝突，以及主管需要協調的一個具體決定。

可以提早向主管報進度，不必等四方完成。四方確認是方案成熟度與協作依據，不是「四張同意票」也不是正式上線驗收。附帶條件需有範圍／責任／後續驗證，不將未採用直接變成對 consumer 的檢討。
