# 探索章程與驗證矩陣

這是後續討論與 agent 工作的共同入口。目的不是累積測試數量，而是讓每個架構主張能被反駁、重現，並指出證據不足的地方。

## 目標與當前決策

在明確的備援服務承諾下，降低系統團隊與 consumer 的整體維運負擔，並呈現提高備援能力所需的成本。不以成本轉移當成節省。

採用主判準：在已界定的營運情境下，各 stakeholder 的價值能支持其投入與責任，且 Reviewer 能據此協調推進。ES 一致性依實際任務及 consumer 契約判斷必要程度，並非提案的最終目的。

現況已釐清：內部已有運行中的 Next.js＋MinIO＋Cronjob＋ReBAC DR，欠缺搜尋、consumer API 與完整權限驗證。主線改為沿用既有 DR 增量補齊能力，詳見 `CURRENT_DR_BASELINE.md`。比較 Web 端嵌入式搜尋與新增獨立搜尋服務的總負擔；不再將 lab 的 ES 視為現行 DR 必須保留的元件。每輪說明支援哪個 stakeholder 決策；未影響任務的完全一致不自動成為必要門檻。

既定範圍：單一 cluster 故障；搜尋／閱讀／下載唯讀；每日同步是工作假設；一小時恢復是討論目標；DR 持續時間未定。不能把討論目標寫成已達成的 SLA。

## 每個主張的紀錄格式

`ID → 主張／適用範圍 → 反例 → 驗證方式 → 預期結果 → 證據 → 對決策的影響`

另記錄 owner、狀態、資料／程式／設定版本，以及重新驗證的觸發條件。owner 未指定就寫「待指定」，不得自行代表團隊承諾。

狀態只用以下詞彙：待驗證、範圍內通過、發現反例、待需求裁定、不適用（需理由）。「測試通過」不能自動把其他環境或正式整合標成通過。

特別注意：揭露舊歸屬風險的測試通過，代表風險可重現，不代表風險已解決。文件存在、Docker config 通過、mock 通過都不能當成完整備援通過。

## 防漏檢查：四個維度，不窮舉所有組合

每次修改主案，檢查以下維度是否仍有未涵蓋的高風險交叉：

1. 使用路徑：搜尋、metadata、分頁／總筆數、閱讀、下載、直接 URL／索引資產。
2. 生命週期：同步、啟動、切換、長時間備援、更新、故障中復原、切回、再次故障。
3. 變化／失敗：角色撤銷、Page 移動或刪除、Media 解除或跨 Space 共用、部分同步、混版、依賴 timeout、磁碟／記憶體不足。
4. 責任歸屬：系統開發、infra、ReBAC、consumer、審核者。每個重要依賴要有 owner 或明確「待指定」。

每項能力至少問：正常可行嗎？不該允許時能阻擋嗎？依賴失敗會怎樣？時間／版本改變會怎樣？目前證據只是在哪個環境成立？

已確認的需求以獨立預期值驗收；尚未確認的產品語意以不同選項呈現，不由測試作者擅自決定規格。

## 討論／實驗紀律

每輪只聚焦一個會改變決策的問題；開始前寫明結果 A/B 分別如何改變主案，以及停止條件。若兩種結果都不影響決策，先暫緩。

會議輸入：主案、差異表、證據、兩三個具體反例。會議輸出：主案缺陷／前提不成立／新增要求／待驗證／接受限制，不以「大家覺得可以」替代紀錄。

實驗卡範本：

```
ID／要決定的問題：
當前主張與適用範圍：
反例／可能失敗條件：
方法：Test / 整合重播 / 故障演練 / 量測 / 設計審查 / 需求裁定
預期結果與其來源（未確認則保留未知）：
資料、程式、設定與環境版本：
證據檔案／命令／觀測：
狀態與限制：
結果 A/B 如何改變主案：
Owner／停止條件／重驗觸發條件：
```

schema、索引設定、權限語意、部署拓樸、API 或 consumer 使用方式改變時，回頭標記受影響的證據需要重驗。歷史證據保留，不靜默改寫。
