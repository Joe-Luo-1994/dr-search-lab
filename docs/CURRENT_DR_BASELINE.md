# 現行 DR 與本輪增量研究基準

更新：2026-11-10。來源：使用者描述現行內部系統；本輪未連線查核正式系統。這是需求與現況資訊，不是雲端實驗結果。

## 三個環境不能混為一談

| 對象 | 已知資訊 | 證據邊界 |
|---|---|---|
| 現行非 DR 系統 | 先前脈絡包含 Backend、MariaDB、ES、MinIO 等；內部 DevOps 實際管理 Infra | 詳細拓樸、版本與故障依賴由 DevOps 補充 |
| **正在運行的內部 DR** | **Next.js Web Server＋MinIO＋Cronjob 備份＋內部 ReBAC 驗證服務**；已有可運作方案 | 權限驗證不完整；沒有原後端 API，因此不支援任何 consumer；沒有搜尋。不能從「運作中」推論完整授權、資料一致性或正式 RTO 已達標 |
| DR Search Lab | synthetic fixture、嵌入式搜尋與實驗 ES、獨立 reader、Linux／Windows 測試等 | 非內部 DR 原始碼或正式部署；lab 有 ES 不代表現行 DR 已有 ES；lab 已驗證讀取不代表正式 DR 支援 API |

PM 已確認 readonly、下載、搜尋方向（依使用者回報），其中搜尋仍是待補能力；需求已確認與實作已存在分開記錄。

## 修正提案起點

主線：在既有 DR 投資上補齊搜尋、核心 consumer API 與授權能力，以可接受的新增開發／維運負擔提升實際使用價值。

之前「保留 ES、精簡整套 Infra」為探索路徑，現在由更具體現況取代：現行 DR 沒有被描述為已部署 ES。是否新增 ES、嵌入式搜尋或保留必要後端邏輯，依任務、相容與成本決定；不為延續既有研究而預設 ES 必須存在。歷史 ES 比對仍是可利用的參考與回歸證據，不改寫結果。

與 DevOps 的初次合作重點：用他們熟悉的既有 DR 為底圖，你提供 Web/API 執行能力可新增哪些責任、需要何種資料、實驗支援程度及成本。不是重教 Infra，也不是把所有東西塞同一主機。

## 三個增量能力及相依關係

| 能力 | 可評估的方向 | 先釐清的核心缺口 | 跨過門檻時的價值 |
|---|---|---|---|
| 搜尋 | 在 Next.js 服務端使用本地／嵌入式索引；必要時增加 ES 等獨立搜尋服務 | 備份是否有足夠 metadata／正文／附件文字、來源版本；資料量、查詢需求、索引發布與權限過濾 | User 找得到資料；consumer 搜尋流程可承接 |
| 核心 consumer API | 在 Next.js server routes 提供必要契約，共用讀取／授權邏輯；缺關鍵業務邏輯才評估保留必要後端 | 先選一個 consumer owner，盤點身份、欄位、分頁、錯誤、下載與切換契約 | 現行僅網站可用的範圍擴展到代表性 consumer，修改成本可見 |
| 授權完整性 | 檢視實際 ReBAC 整合與所有輸出路徑 | 身份、可見 Space、Page→Media、搜尋 metadata、直接物件 URL、失敗拒絕及舊歸屬時效；哪些實際缺失尚未查核 | 網站與 API 具共同可信存取邊界；不能只因呼叫 ReBAC 就視為完成 |

授權問題與搜尋／API 平行釐清：它決定搜尋過濾、總筆數／分頁、下載 URL 和快取，不能等功能完成才補。上述項目是稽核問題清單，不聲稱現行系統每一項都已確認存在漏洞。

沿用 Cronjob／MinIO 的可行性須查來源資料集合、完整性、發布／失敗狀態與讀取方式；不預先要求更換它們，也不假定已有 release manifest 或原子切換。M01 只驗證候選模式；先把實際備份契約與缺口盤清，再決定實驗切片。

## 內部 v1 的比較方式

- A：沿用既有 DR，Next.js 增加 API＋嵌入式／本地搜尋，補授權及資料發布。新增服務較少，但應用資源、索引更新、語意差異與維護成本需驗證。
- B：沿用既有 DR，Next.js 增加 API，新增獨立搜尋服務並補授權／發布。可能更接近現行搜尋行為，但多出部署、備援、升級與資源責任。
- C：核心 consumer 或來源依賴證明必要時，保留所需後端／資料服務。可重用邏輯，但須比較新增棧的成本；不是預設重建全套。

先比較 A/B，C 作有條件備案；不平行實作三套。現有 lab 的嵌入式與 ES 證據都可用來縮小未知，正式選型仍待 DevOps、consumer 與 FDE 意見。
