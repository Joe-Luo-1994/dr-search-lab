# DR 研究與採用 roadmap

日期：2026-11-10。這是建議工作節奏與探索預算，不是已排定會議、已承諾工期或服務 SLA。使用者同時準備方案、釐清需求與探索可行性；主管關心可見推進。各對口 owner、可用工時與會期待指定。

## 現況修正：沿用正在運行的 DR

依使用者最新描述，既有 DR 為 Next.js＋MinIO＋Cronjob＋內部 ReBAC，已運行但權限驗證不完整、無 consumer API、無搜尋。詳見 `CURRENT_DR_BASELINE.md`。R0/R1 從這個實際基準開始，與 DevOps 盤點備份資料及 Web 可承接的能力；先形成增量方案 v1，再請 FDE／一個核心 consumer 挑戰。搜尋與 API 的授權需求平行確認。Lab 的 ES 不是現行 DR 元件。

## 成果定義與目前位置

目標是可採用的營運持續能力。每輪至少交付：可檢視成果、改變的判斷、下一個有界投入。能力提供、consumer 整合、維運採用分開追蹤；整合困難留在方案缺口中，不因工具交付就轉成對其他團隊的檢討。

已有：使用者回報 PM 已確認 readonly、下載、搜尋功能方向；合成唯讀流程與雲端冷啟動證據、失敗紀錄、核心假設、公開先例、M01 實驗卡。缺少：代表性業務任務、正式 client 契約、授權時效裁定、真實 MinIO 發布證據、非作者操作與成本基準。現階段為 R0 準備進 R1；不能稱已可正式採用。

## 主管要求的四個角色確認

依使用者補充，第一輪聚焦一個核心 consumer owner 的方案確認、團隊核心 DevOps 對資源限制／架構合理性與共同報告的認同、PM 的 user 需求確認，以及 FDE 的內部技術可行性／選型諮詢。詳見 `STAKEHOLDER_CONFIRMATIONS.md` 的狀態、會議問題與紀錄格式。PM 功能方向已確認，其餘確認尚未取得；不得擴寫為正式驗收。

版本里程碑依使用者策略修訂：R0 準備應用／資料側候選做法，R1 前段與熟悉現行 Infra 的核心 DevOps 共擬內部 v1；取得現階段可行方向後，R1 後段攜 v1 請教 FDE 與一個核心 consumer owner（可並行），PM 補情境／時效細節。依挑戰及必要的 R2 小實驗形成 v2；不等完整技術實作才徵詢。R3 是後續整合／接手驗證，R4 為投入／試行決策。v1→v2 是近期主管可見成果，R3/R4 不被混稱為已完成。等待對口時可做不依賴答案的合成工作；涉及缺失前提的正式承諾維持待確認。

## 路線與可展示成果

探索預算以方案準備者的有效工作日計，外部等待另記；上限到期必須交付目前結果並決定縮範圍、轉向或停止，不自動加碼。數字為初始建議，主管可調整。

| 階段 | 本輪問題／預算 | 使用既有資源 | 可展示成果 | 對口確認與出口 |
|---|---|---|---|---|
| R0 對齊方向 | 要保住哪個任務、值得找誰參與？1 工作日 | 既有研究、測試報告、假設與公開基準 | 一頁情境提案、選項表、前三個未知與合作請求；本文件附初稿 | 主管確認優先情境與協調窗口；無回覆仍可做 synthetic，但不得當業務認可 |
| R1 早期排除致命前提 | 唯讀／資料時效／授權／client／資源是否讓主案不成立？2 工作日 | 現有 demo、p09 反例、對方既有文件與一個使用流程 | 最小服務契約 v0.1、依賴圖、成本分布表；未回答項明列 | 產品／授權裁定高影響項；consumer 指出必要契約；資源與 DevOps 先看限制。遇不可接受前提先轉案 |
| R2 最小端到端證據 | 不完整發布時，完整操作鏈能否保住？3 工作日，開工前依 M01 再估 | 現有 fixture、sealed ES、reader、runbook；真實 MinIO 取得條件先核對 | 限定故障時間線、兩程序 synthetic HTTP 鏈、client 額外負擔與失敗理由；不必等全部案例才展示 | 每個有結論的小切片即回報。依 M01 正確性／120 秒單案例界線停止；無 MinIO 能力就報阻塞，不用 mock 宣稱通過 |
| R3 整合與接手試走 | 實際使用者與非作者能否使用／操作？準備與整理2工作日，試走另約 | 一個已取得的代表性 client、R2 證據、既有操作文件 | 整合差異、求助次數／原因、人工步驟與owner缺口 | consumer／DevOps 指出可接受與不可接受項。沒有正式 client 或操作者時只稱合成／桌面預演，不升格驗收 |
| R4 選案與有限試行決策 | 哪個選項值得下一筆投入？1工作日 | 各輪成果與成本／風險紀錄 | 主案＋備案、適用限制、投入／責任、試行及退出條件 | 主管／Reviewer 協調資源與具名接受；尚缺條件則先縮小範圍，不直接宣布上線 |

R1 的對口釐清與 R2 不依賴該答案的 synthetic 工作可並行。已知可能讓架構翻盤的問題優先問，不等原型完成才找授權／資源團隊。正式未知阻塞正式承諾，不必阻塞所有可逆探索。

## 未知的策略性確認

| 優先未知 | 最便宜的第一步／帶入素材 | 找誰／具體決定 | 未獲答案時可以做什麼／何時不可繼續 |
|---|---|---|---|
| 哪項營運任務值得保住 | 用 runbook 搜尋→閱讀→附件作候選，請對方替換成實際工作 | 主管／業務代表選1個優先任務、指出不可接受降級 | 繼續合成；R4 不宣稱業務收益已成立 |
| 舊內容與撤權／移動時效 | 帶 p09 反例、可用性與拒絕服務兩個結果 | 產品／授權對口裁定時間與失聯政策 | 獨立測版本一致性；R3正式交付政策不可擅自通過 |
| consumer 最小相容契約 | 先請一份去敏 request/response 或既有流程說明，再展示合成契約差異 | consumer 維護者挑1流程、列必需欄位／錯誤／分頁 | 合成 HTTP 不等待完整規格；正式相容保留未知 |
| 故障域與可用資源 | 現有拓樸／資源規範優先，不另建平台盤點全公司 | 資源提供者＋DevOps確認身份、網路、儲存、配額與責任邊界 | loopback 研究可繼續；不得聲稱跨區獨立或正式容量 |
| 誰能維護與投入是否值得 | 列發版、故障、升級、清理的作業，請對口估頻率／工時範圍 | 主管與維護者協調ownership、可投入上限 | 先報粗估及信心範圍；無維護責任不過R4 |

每個未知記錄：問題、影響哪個決定、暫定假設、證據／來源、owner、下一次檢查點、沒有答案的處理。優先順序依「翻盤影響、取得答案成本、是否阻塞最近交付」判斷，不依技術有趣程度。

## 會議使用規則

不自行寄信或約會；目前只準備素材。先利用文件／非同步回覆，仍有衝突或取捨時才開定向會議。

- 主管／Reviewer：建議20分鐘，帶一頁情境、選項及一個合作請求；取得範圍／對口／有界投入決定。
- 產品／授權：建議30分鐘，帶一個具體反例與兩三種處置代價；取得政策答案或明確owner與回覆檢查點。
- Consumer：建議30分鐘，帶實際或合成操作鏈；辨識必要契約與最小可合作流程，不先要求改系統。
- DevOps／資源：R1短檢視、R3實際試走；先排除不可用的依賴，後觀察是否能接手。

會議輸出為一項決定、假設修訂或具名待辦；「大家聽過了」不算驗證。未採用先追查方案／資源／責任障礙，不預設對方不配合。

## 主管可見的節奏與探索上限

每兩個有效工作日至少有一次可見更新，或遇到關鍵反例立即更新，不等階段結束。外部等待在檢查點顯示等待項與並行進展，不以不斷開新題掩蓋阻塞。

固定五行：
1. 本輪可展示的成果（連結／操作／證據）。
2. 因此可以多承諾什麼，仍不能承諾什麼。
3. 對哪些團隊減少或增加了負擔。
4. 最大阻塞與需要主管協調的一個決定。
5. 下個有界投入與停止／轉向條件。

一次只主攻一個採用障礙，至多比較主案與一個有觸發條件的備案；完整棧維持參照。已有可信來源與可反駁假設後，暫停泛搜；要新增研究題須說明如何影響最近決定。成本尚無實測時不捏造精確ROI。

## R0 一頁提案初稿：現在就能拿去討論

**候選情境（尚待業務確認）**：主要知識服務 cluster 中斷，使用者需要找到處置文件、讀正文並取得附件。哪個廠區／角色、哪個任務最重要，請主管協調確認。

**已確認功能方向**：依使用者回報，PM 已確認 readonly、下載、搜尋。

**擬保障能力**：有限唯讀流程；使用完整且標明時效的副本；維持授權，故障與降級可判讀。資料年齡、恢復時間及正式相容門檻待裁定。

| 選項 | 能得到什麼／可能成本 | 目前證據 |
|---|---|---|
| 既有運行中 DR：Next.js＋MinIO＋Cronjob＋ReBAC | 沿用現有投資；尚缺搜尋、consumer API，權限驗證不完整 | 使用者回報現況；實際程式／資料與操作待共同盤點 |
| 有限唯讀備援 | 聚焦重要讀取任務；新增匯出、版本發布、API適配及維運責任 | 合成讀取與正常冷啟動已驗證；正式整合待驗證 |
| 較完整備援棧 | 有機會重用更多行為；複寫、資源與演練成本需估 | 本案尚未做完整獨立復原驗證 |

**目前進展**：36 tests、17整合、128搜尋比對、417閱讀、425下載為雲端合成證據；非正式SLA、全產品相容或總成本證明。公開先例支持繼續研究發布／回退模式，不能代替本案驗證。

**本次合作請求**：主管協調一個核心 consumer owner、團隊核心 DevOps 與 FDE 諮詢窗口，PM 依已確認功能補充代表性任務與降級細節；涉及授權／資源問題再找實際 owner；先投入R1限定釐清，不要求先承諾全案開發。

**下一個可交代成果**：服務契約v0.1、可能翻盤的前提、最小實驗及每方工作量；依結果決定進R2、縮小範圍或改用保留原元件的備案。涉及正式資源／責任由具權限者確認。

## 近期準備重點：提供 DevOps 缺少的選項

以下是早期責任比較，最新選項優先序以 `CURRENT_DR_BASELINE.md` 為準：既有 DR＋Web 本地／嵌入式搜尋（A），對比既有 DR＋新增獨立搜尋服務（B），必要時保留後端（C）。不將「保留 ES」當成既有部署事實。

先做一份應用責任比較：

| 候選方向 | 準備者要提供的證據／資訊 | DevOps 共同評估 |
|---|---|---|
| 必要 web server＋較完整讀取服務棧 | 哪些必要行為／相容性可直接重用、有哪些依賴 | 既有維運方式可否沿用、資源與恢復成本 |
| web server 承接唯讀 API／內容組裝，保留 ES 與版本化副本 | 合成 reader 證據；匯出、授權、發布、下載與 API 邏輯的責任 | 節省哪些部署，新增哪些工作、資源競爭與故障範圍 |
| web server 搭配本地資料／嵌入式搜尋（有觸發條件的備案） | 既有嵌入式測試、搜尋語意與容量缺口 | 獨立服務減少是否值得應用耦合與相容性成本 |

此處 web server 表示必要的網站／API 執行能力，不先鎖死同程序或同主機拓樸；選擇依資源與故障限制共同判斷。上述為比較素材，非要同時實作三套。對內分享的主軸是可替代哪些責任、留下哪些成本，而非搜尋引擎基本概念。
