# N1 結果與下一個決策（執行中）

本輪要回答：在有限原生最佳化後，SQLite 是否已足以承擔 DR 搜尋；若不足，Tantivy 的能力增益是否值得新增維護責任。不是比較一個引擎名字誰最快，也不是公司正式容量驗收。

## 已完成的資格驗證

- SQLite S0/S1 × E/L：32 個人工 golden cases，共 128 次通過。S1 使用原生 rank，仍保留精確 total、title 權重及 pageId 同分次排序。
- Tantivy E/L：相同 32 個 cases，共 64 次通過。採原生查詢、結構化 filters、TopDocs/count；沒有針對題目快取答案。
- 中文詞項檢查最初失敗：手寫「排程」分詞期待不符本機 ICU。獨立核對 52 個欄位後，只修正期待並保留失敗原檔。這證明受控 index/query 詞項一致，不證明真實中文搜尋品質。
- Tantivy 初次 Rust 1.88 建置失敗；同 Cargo.lock 改隔離 Rust 1.90 後成功。工具鏈、binary 散布與升級回歸列為新增責任。

## G2 已通過，G3a 尚在驗證

G2：百萬合成文件、21 題、每題每區塊 30 次正式量測，兩引擎各三區塊交錯執行。每個 reader 4 CPU／8 GiB，E 契約保留精確 total、授權／Space／Tags AND 與同分 pageId 排序。六區塊均通過，共 3,780 次正式查詢；完整來源／索引 hash 前後相同，reviewer 已核准 G2 有限結案。

證據：[彙整](../evidence/n1-native-20261117/formal-summary.json)、[設計與獨立審查](DR_N1_DESIGN_REVIEW_20261116.md)。彙整檔 complete=true；各題各區塊 n=30，不合併百分位。常見詞 SQLite P95 825–850 ms、Tantivy 7.86–8.08 ms；長常見詞組 SQLite 1,659–1,682 ms、Tantivy 12.62–12.68 ms；稀有詞兩者皆低於 1 ms。這些是此配置 round-trip 描述，不是純引擎倍率或 HTTP 容量。

G3a：預載索引的 Next.js Web／consumer／閱讀／下載混載。先一次閱讀 baseline，再 W 三次，通過才進 M 三次；不縮短測量窗。SQLite 4 個通用 worker，Tantivy 2 個搜尋＋2 個 metadata worker，同 Next 總配額。此為整合配置比較，不是只換引擎的因果實驗。

G3b：從 MinIO 下載索引＋metadata、新舊版本切換及失敗回復。本輪 G3a 不包含這些能力，不能把 G3a 通過當成完整 DR 可部署。

## 維運成本不能從索引大小直接推論

SQLite 檔案約 3.31 GB，包含全文、metadata 及 FTS。Tantivy 索引約 99.9 MB，但本輪仍保留完整 SQLite 作閱讀 metadata；兩者儲存內容不同，不能宣稱儲存縮小 33 倍。Tantivy 此整合的本地資料反而是兩份相加，更新時還須考慮雙版本。

兩方案都需要版本發布、下載驗證、資源配額、排隊、授權接縫及失敗處理。Tantivy 額外增加 Rust 建置／binary／IPC／多角色程序管理與多 artifact 一致性；SQLite 原生 rank 改動較小，但是否足以滿足混載仍要實測。詳見[工程與維護責任帳](DR_N1_OPERATIONS_LEDGER_20261117.md)。沒有可靠人工工時或公司 owner 資料，不能據此給出月維運工時或最低 TCO 結論。

## 解讀邊界

- 合成語料高度重複；正式文件、查詢分布及 ReBAC 延遲未知。百萬索引僅256頁發布正文，Web固定p000001/p000002、附件8個（4×64KiB、3×2MiB、1×8MiB）；不證百萬頁內容已完整發布或所有搜尋結果都可閱讀。名為pdf的百萬查詢也不是PDF-only抽取驗證。
- G2 串行延遲不是 RPS 或 API P95；Tantivy 的分詞在 G2 parent，SQLite 在 reader，不能把 round-trip 比值稱純引擎倍率。G3a 分詞回到 Next 配額內。
- 未清除 OS cache；完整 hash 和 warm-up 可暖快取，不稱冷啟恢復時間。
- G3a 每 engine 連續執行以保留同 baseline/PID；SQLite 先、Tantivy 後，跨時間漂移需明示。
- 單個 worker timeout 會讓此保守 adapter 關閉整個 pool。需區分首因與後續連鎖拒絕；整合配置可因此不合格，但不能把全部拒絕視為引擎直接失敗。
- A 完整沿用仍是可行基準；本輪沒有新跑 A／ES，不能用 B 或歷史不同契約數字代替。

本文件待正式 gate 結果更新；本輪新增材料尚未公開發布。

G3a 首次 SQLite 短測 13 項通過，但閱讀 baseline 啟動前兩個 systemd unit 已共同停止，loader 因 cgroup 路徑不存在判儀器無效。無正式容量證據；保留 attempt1，改單一持續 WSL 控制程序後才以新 attempt 重跑。不是 SQLite 容量失敗，沒有證據稱 WSL 重開機。

### G3a SQLite attempt3：基線通過，Web 暖機未通過

閱讀 baseline 正式 300/300 成功，P95 13.44 ms。W1 暖機最早 Web restricted 查詢旅程達 4 秒截止，隨後出現 SEARCH_BUSY 與 POOL_CLOSED；最近 status 顯示四個通用 worker 忙碌、queue 16。暖機即停止，正式測量全部未送，故不報正式 0 RPS 或 100%實測錯誤率；W2/W3/M 未測。

短暫資源樣本沒有 OOM／CPU throttle，尚不能確定 worker 內部首因，也不足以據此增加 CPU/RAM。此結果支持先測相同資源的 Tantivy，不支持宣稱 SQLite 普遍不可行。Tantivy 13項短測已通過，正式序列執行中。

證據：evidence/n1-native-20261117/g3a-sqlite-attempt3/summary.json；暖機 raw、status 與 resources 都保留。

### Tantivy 階段性證據（仍執行中）

Baseline 300/300、P95 11.23 ms；W1 閱讀300/300、P95 12.54 ms，Web1200/1200、P95 23.26 ms，零漏發／錯誤。同PID、配置、boot ID；reviewer已讀回。尚不能以W1代替三輪或M。
