換一個程序，能找回應該服務的版本嗎？

四個正常啟動案例還檢查搜尋、Tags AND 篩選、版本差異、正文、SSR 頁面、附件、受限身份與舊版連結。兩個反例故意讓 manifest hash 與核准指標不符。

證據能支持到哪裡？

45 筆 HTTP：33×200、7×404、3×409、2×503。404 是受限頁面或停用的熱更新入口；409 是舊版連結；503 是壞指標。這些都符合各自預期，不能統稱為 45 次使用成功。

搜尋回應由凍結 controller 當場斷言，未完整保存正向 body；reviewer 沒有宣稱離線重算所有搜尋欄位。正文與附件另有回應 hash 對照。629 個凍結檔獨立重算無變化，含原 K5 的 80 檔。

02 · 機制

遠端說「應用哪版」，本地記「已驗哪版」。

發布端
上傳不可變 DB、正文、附件 → 逐檔讀回驗證
↓
上傳並驗證 manifest
↓
最後寫入 approved：核准版本與 manifest hash
異地 MinIO → 新啟動的 Next／SQLite 程序
啟動端
讀一次 approved，固定此次候選
↓
核對 manifest → 下載 DB 或驗證已有快取
↓
Pool 檢查 SQLite 與版本身份
↓
提交本地 active → ready，開始接請求

approved 是受信任發布端指定的版本；active 是本地通過驗證的安裝紀錄。不是掃描檔名挑最大，也不是只看本地 active 就假定它仍是核准版本。

快取與版本的保護

每個版本以 release ID 與 DB hash 隔離；相同 release ID 換內容會被拒絕。下載先進 staging，驗證後再安裝。已有 DB 仍完整重算 hash。每個程序使用自己的快取，沒有驗共享 PVC 多 writer。

本輪以單一可信 publisher、共用研究 root credentials 執行；正式 IAM 分權、簽章與多發布者競爭尚未驗證。client GET 紀錄不是 MinIO server audit。

03 · 維運代價

少一個手動步驟，多一組需維護的契約。

已消除的原型操作

重啟時不必人工把本機版本描述或 V2 路徑交給 reader；同快取與空快取均從遠端選版。

沿用的部分

Next build、SQLite pool／worker、下載與 hash 工具沿用；沒有新增常駐服務種類。正文與附件仍從異地 MinIO 讀取。

新增的長期責任

維護 publisher 發布順序、bootstrap 驗證鏈、版本 identity 與 active 提交、快取驗證，以及批准錯誤的診斷與處理。這些是需有 owner 的程式與發布流程。

還沒量到的成本

非作者操作時間、月事件頻率、on-call 工時、正式部署模板與整套 A 的既有自動化成本都未知。controller 是實驗工具，不能全部當成日常人工作業，也不能當作免費。

04 · 尚未決定的可用性取捨

指標壞了，新程序目前拒絕服務。

即使有好快取，本版也不擅自服務舊資料。本次壞 hash 案例保住了 cache 與 active，但「保住舊檔」不等於「自動回滾並繼續服務」。

修復遠端指標後，失敗程序的自動重試、重新啟動與告警尚未實作／驗證。本輪最後恢復有效 V2 指標並停止實驗服務。

下一個有價值的決策：核准指標出錯時，要等待修復，還是允許已驗證舊版服務？後者需界定可接受的資料與權限陳舊程度，不能只視為技術優化。

本輪停在此處。熱更新入口刻意停用；O1 啟動流程與 K5 熱更新尚未整合，不能把兩份實驗直接稱為完整發布系統。V3、GC、rollback、Kubernetes 故障與 worker fatal 復原留待後續選題。
