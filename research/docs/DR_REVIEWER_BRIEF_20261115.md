## 第1頁：目前是否值得繼續？

**建議：繼續把本地 SQLite 副本做成可操作的第一版候選，同時保留「整套沿用」作成本基準；現在不核准正式採用，也不宣稱較省總維運。** 百萬合成資料的儲存／查詢路徑已有有限證據，真正的基本功能、consumer、授權與事故恢復仍有缺口。

我們要讓廠區使用者及既有 API consumer，在台灣指定 cluster 失效後，仍能搜尋有權限的內容、閱讀並下載附件；同時降低產品、consumer 與 Infra 的合計開發和維運負擔。服務數較少只是手段，不能代替這兩個目標。

**範圍基準：** 唯讀；故障域是指定 cluster，不是整個台灣斷線；其他 cluster 可到達，ReBAC 有備援是工作假設。DR 要支援多久未定，不能只測一小時存活就算足夠。每天同步一次是初始方向，不等於已證24小時RPO。事故後約一小時恢復是早期討論起點；文件裡的15分鐘整體恢復、120秒 reader 恢復、2秒搜尋等是研究提案，不能升格成對口已接受的需求。

| Reviewer 先問的問題 | 現在的答案 | 對決策的影響 |
|---|---|---|
| 基本任務都能完成嗎？ | **尚未完整證明。** 合成搜尋／閱讀／小附件鏈成立；Tags AND未納入百萬harness，正式consumer、入口／身份、真實授權與內容仍未整合驗收 | 可核准下一段整合，不能核准上線或完整DR承諾 |
| SQLite百萬頁路線有明顯技術阻礙嗎？ | 在這份資料與短循序工作集中未出現；三回合查詢觀察均低於0.8秒 | 值得保留候選；不等於一般搜尋品質、持續併發或SLO成立 |
| 少了搜尋服務，代價搬到哪裡？ | 每reader約2.13GB副本；替換時兩份約4.27GB；新增產製、校驗、版本、worker、告警與清理責任 | 必須與整套沿用的實際操作成本比較，不能只比Pod數 |
| 事故時要等多久？ | 20MiB/s應用節流下，空副本到首條合成鏈約107.52秒；不含切流、登入、上游發布等 | 能討論副本準備方式，尚不能回答完整RTO |
| 為什麼不用原 Backend＋ES 就好？ | 它是有效備選，可能更能沿用既有技能和API；目前沒有公平的總成本比較能排除它 | 若沿用成本更低，或SQLite所需妥協不可接受，應改選沿用 |

**本次希望得到的評審結論：** 是否同意以相同基本任務比較「整套沿用」與「SQLite候選」，先補關鍵流程及維運證據；哪些服務承諾是必要、哪些可交換成本。不是要求 reviewer 在缺少正式證據時先選引擎。

## 第2頁：任務是否成立？缺口與妥協分開

「有限已證」只涵蓋列出的實驗範圍；「未驗」不是不可行；「已知差距」不是對口已接受的妥協。不把它們換算成完成百分比。

| 情境／成功條件 | 現況與依據 | 若現在交付會怎樣？／下一個閉合方式 |
|---|---|---|
| 原站失效後，使用者與consumer找到可用DR入口並登入 | **未驗**：真導流／身份／完整故障域演練缺證據 | 尚不能保證進得去；畫清入口與依賴，再做完整故障任務 |
| Keyword＋Space＋多Tags全部符合，找到可採取行動的page | Keyword/Space在合成語料**有限已證**；本輪**未測Tags**、真實相關性和原ES語意 [E1] | Tags是既有基本需求，不能默默刪除；先補共同契約、oracle與任務；ES等價程度另向consumer驗證 |
| 搜尋後看到正確正文、下載同版且有權的附件 | 純文字正文與68-byte附件、受控Space及page membership**有限已證** [E1] | 真Lexical、大附件、page移動／撤權／ReBAC未知時的處理未完成；合成權限不能作正式保證 |
| 既有consumer完成原本工作，改動量可承擔 | **未驗正式相容性**：目前Node HTTP harness，不是正式consumer；歷史Next測試僅子證據 [E1,E4] | 需要欄位／分頁／錯誤／重試契約及代表client；沒有「零改碼」證據 |
| reader重建時，既有使用者仍可工作 | 百萬舊reader與新副本下載的60次循序查詢重疊**有限已證**；新PID讀新副本成立 [E1] | 不等於多人負載或零中斷切換；尚需流量路由、在途請求與回滾驗證 |
| 更新資料後，搜尋所得舊連結仍可閱讀與下載 | 歷史原型跨reader可能409，對透明續行是**已知差距**；最新實驗只有同release替換 [E1,E4] | 透明續行要版本保留／路由；或提議清楚的重搜/重試。後者需consumer接受，不能自行改成需求 |
| 資料有時效且事故持續時不失控 | 資料age策略、每日產製失敗處理、長時運作與實際RPO **未驗** | 顯示資料cut時間／狀態，定義過期策略、告警與處置；同步頻率不是資料時效保證 |
| DR的MinIO又失聯，仍可閱讀／下載 | 是更強故障組合；最新L附件仍取MinIO，不能套用歷史完整local bundle的離線證據 [E1,E4] | 若要求額外容錯，另列必要內容本地化或替代來源的空間／同步成本；基本版也須明確錯誤與重試 |

所有候選都用同一張任務表。保留ES不自動補足入口、內容一致性、權限與恢復；SQLite已完成的局部實驗也不能代替整體任務。

## 第3頁：為什麼這樣拆？是否真的比較省？

下表是三種完整方案的比較框架，不是已驗收的排名。真正比較前，應固定相同的基本任務、資料時效、站點數、流量和恢復承諾。

| 路線 | 希望沿用／減少什麼 | 新增或仍須負責的工作 | 目前證據與可能翻轉條件 |
|---|---|---|---|
| **A 整套沿用**：Next＋Backend＋必要MariaDB／ES／MinIO與授權整合 | 沿用API、商業邏輯與現有操作經驗，降低新相容性工作 | 跨站副本、資料同步一致性、容量、升級、故障切換、唯讀限制與演練；Backend是否仍需要MariaDB必須查證 | 尚未實測完整DR副本及總成本。若既有部署／備份／告警可直接沿用、額外成本低，可能是最佳選擇 |
| **B 保留ES，重做周邊**：Next adapter＋ES＋版本化內容 | 保留ES搜尋能力，嘗試減少Backend／MariaDB | Next API／授權／內容adapter、版本協調，另加ES維運；不是A的零改動縮小版 | 歷史ES合成容量子證據不等於這個完整組合驗收。若consumer高度依賴ES語意，可優先於換引擎 |
| **C 本地SQLite副本**：Next＋本地搜尋／內容artifact＋MinIO＋授權整合 | DR端不另部署ES搜尋服務；副本可重新取得 | 上游一致抽取與產製、完整性／發布、worker／超時、版本保留、下載／ready／GC、API與授權整合 | 最近三輪支持有限容量與副本替換 [E1]；只有新增工程與維護代價低於A/B時，才有總成本優勢 |

**Backend＋ES不是零維運；但「沿用成熟流程」可能比維護一套新流程便宜。** C不是因為服務較少就比較合理。反過來，也不能把所有方案共通的DR成本只算在C頭上。

對C，應沿兩條路徑檢查設計：

- **平時準備／更新**：上游一致抽取→產製版本→發布到DR物件儲存→reader下載、校驗、ready→保留／回收舊版。這些責任沒有因移除Backend或ES而消失；端到端自動化尚未證。
- **事故中服務**：入口／身份→可信Space判斷→查詢／閱讀→page→media membership判斷→取附件。Next是候選服務入口；本輪測的是harness。正式ReBAC契約與current membership一致性尚未證。

### 成本頁只展示有決策意義的數字

| 本地SQLite的觀察 | 解讀邊界 |
|---|---|
| 這份百萬合成artifact 2.13GB／reader；保留新舊兩份約4.27GB | 含索引及合成正文，未含真實附件總量；不是公司百萬頁容量預估 |
| 完整GET＋hash在20MiB/s節流下約107秒；無節流同機首鏈4.19秒 | 已暖OS cache、同機loopback；不含DNS／身份／產製，不能當完整RTO |
| reader取樣RSS約83–117MiB；同機受測程序合計峰約653–675MiB | OS cache不在RSS內；WSL約19.53GiB RAM、28 logical CPU，未設cgroup限額；**不能據此配置128MiB Pod** |
| 背景下載中60次查詢皆正確，最慢0.78秒 | 一次只發一個查詢，之後等1秒；不是固定到達併發，也不是30分鐘穩態 |

現有不同日期／機器／harness的ES與SQLite速度，不放進同一張效能排行榜。A/B的同範圍資源與人工成本空缺，直接寫「未量」，不填估算假裝比較完成。[E1,E4]

### 要比較的是誰多做了哪些事

| 成本 | 公平比較方式 | 現況 |
|---|---|---|
| 一次性開發／consumer改動 | 分列沿用、修改、新建的模組及代表client改動；共同DR工作另列 | C責任已盤點；A實際可沿用程度、工時未核實 |
| 常態資源 | 同站點／副本／資料保留政策下，比CPU、含cache記憶體、磁碟、流量、更新峰值 | C有局部觀察；A/B對等數據未量 |
| 例行維護 | 固定期間內的版本升級、產製失敗、過期告警、清理與回復步驟，標owner及人工介入 | 尚無真實工時或接手證據 |
| 事故操作 | 同一故障卡、由非作者依runbook操作，記步驟、主動操作時間、等待、求助與失敗恢復 | 尚未做同條件非作者比較；agent耗時不能代替值班人員工時 |
| 長期維護風險 | 新增自有程式、版本耦合、技能集中、診斷難度與誰負責修補 | 可列風險，不能虛構金額或發生率 |

## 第4頁：怎麼讓這次review有結果

### 有需要協商時，帶交換條件

| 需求變化 | 可提出的選項 | 代價與接受者 |
|---|---|---|
| 冷恢復不能等完整下載 | 平時預熱副本；若仍不夠再驗H背景補齊，或沿用熱備服務 | 常態容量／同步／健康檢查；Infra與服務owner。H未證可直接滿足 |
| 必須維持既有搜尋語意／API且consumer少改 | 優先盤點A；也可評B保留ES | 更多部署依賴與同步責任，換較少客製搜尋相容性工作；consumer及Infra確認 |
| 切版後不能要求重搜 | 增加舊版本保留與路由／鏈契約 | 更多版本空間與協調；provider負責實作，consumer確認任務成功 |
| 最低硬體資源或更高並發很重要 | 同資源限額、同工作集測A/B/C，再比較 | 目前低RSS不足以回答；不能靠減少功能讓某方案勝出 |

新增情境時，先標記它是既有基本需求、合理的新承諾或更強故障組合，再指出現方案狀態、最小改動／替代路線、誰多付什麼成本及需補哪項證據。真正未知就保留未知；不因做過很多實驗而承諾有備案可涵蓋80%。

### 本次建議的評審裁定

1. **目標尚未全部成立，但技術候選值得進下一段。** 優先補AND Tags與一條可操作的Next／合成consumer任務鏈；正式授權、入口與內容驗收保持必要缺口。
2. **不先裁定C比A省。** 同步做A的依賴／部署／備份／告警／操作盤點，將「沿用可省多少工作」具體化。這是下一次選型缺少的關鍵證據。
3. **訂出翻轉條件。** 若A可低成本沿用，或C的新增維護超出團隊承擔能力，選A是合理結果；若C能完成基本任務且總負擔較低，再支持C。既有研究投入不構成繼續選C的理由。

Reviewer可選的結論是：支持補證、要求縮小／調整服務承諾、改以沿用作主案，或因必要缺口暫不批准。紀錄需寫「因哪個情境／成本、尚缺什麼、由誰接受」，不能只記「架構合理」或「再研究」。
