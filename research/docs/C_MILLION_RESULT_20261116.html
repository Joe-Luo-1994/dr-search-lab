02 · 為何會互相影響

SQL 離開主執行緒，仍共用 Pod 預算與排隊。

Web 使用者 ＋ API consumer
兩條獨立到達流量，沒有 Web 優先配額
↓ 同一個 Next reader
2 CPU／4 GiB（唯一備案）
Next SSR、API、內容代理、下載與 hash
↓
共享 queue → 2 個 SQLite child workers
搜尋與 page metadata 都使用這個 pool
本地資料包 V1 3.313 GB；更新時保留新舊版

consumer 4/s 階reader平均約1.98核等值、共享pool取樣排隊最多8個；Next event-loop最大觀察延遲約24ms（量測解析度20ms）。這支持先調查SQL／共享排隊與CPU預算，不足以把原因歸為Next主執行緒卡住。

↓ 正文／附件取件；安裝及更新下載 index
獨立 MinIO：4 CPU／4 GiB
同一台 WSL 主機、本機網路；非跨區性能保證
ReBAC 本輪以合成身份模擬，沒有量公司授權服務
1 GiB 為何沒繼續測？

3.313GB 下載／hash 約9.75秒完成；pool啟動檢查超過原30秒期限。memory.max事件34,832、檔案快取反覆回收，CPU限流約0.016秒、OOM0。它支持優先試較大記憶體，不證明唯一根因。4GiB備案保持CPU／worker／查詢／期限不變，下載約9秒、檢查約5秒；先後順序與主機快取有干擾，未作冷快取因果實驗。

原 formal-1 未發出正式負載；其 freeze 是失敗後保全。fallback-1 則在ready後、負載前凍結，兩份各68項後驗均無差異。

配額不是實際常駐消耗；集中builder與publisher不在reader預算內。每個Pod下載各自版本，多站／多Pod需累計。索引已含可搜尋文字與metadata；附件大多不在SQLite，但不能假設索引必然小到可忽略。

新增實作與維運責任
  • stream發布與讀回hash，避免中央工具把整個3GB包塞入記憶體。
  • 共享worker pool、排隊／硬期限、worker失敗回報；若增加優先或獨立pool，會再增加責任。
  • SSR與API走同版metadata與內容，授權／錯版／重搜契約需接正式系統。
  • 版本安裝、完整檢查、舊版保留、新舊切換、磁碟護欄及資源監控。
  • 研究工具：compact source oracle、獨立Web/consumer到達流量、逐任務量測與freeze，非全都產品常駐成本。

人日、token金額、公司infra單價與A完整方案每站增量皆未知。本輪不宣稱C總成本較A低，B也不是A的替身。

05 · 帶回團隊的具體決策

先補更新，再決定如何保護 Web。

Reviewer建議下一個有界實驗優先只把reader RAM 4→8GiB，保持2CPU及2/s consumer＋2/s下載，驗證更新重疊資源是否足夠。這尚未執行，也不代表已決定採用8GiB；若仍失敗或成本不可接受，再考慮獨立新reader準備／切流或保留原完整服務。

增加RAM不會自動回答Web干擾。 consumer 4/s時CPU已接近2核預算；Web優先排程／consumer限流／獨立資源是另一項待驗決策，不能把更新修好當成兩題都解決。

若DR允許限流，保留C但需驗證consumer預算／Web保護，並處理更新資源。若consumer高峰或相容性要求使此類自有控制成本過高，回到A完整服務部署，或另外驗獨立搜尋服務的方案；目前沒有同條件成本勝負。

本輪只用了事先批准的唯一記憶體備案，沒有在失敗後改查詢、放寬期限或反覆加資源追求通過。後續以實測失敗位置選一項變因，不擴散成全面引擎比賽。
