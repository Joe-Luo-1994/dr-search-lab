哪個方案，
讓 DevOps 少花工？

目標是找出能讓 Web 與 consumer 完成搜尋、閱讀、下載，且多處備援時整體維護負擔合理的配置。SQLite 是候選，不是預定答案。

首要目標是長期維運工作量。較少 deployment unit 是待驗的優勢；硬體與容量用來確認方案撐得住。先盤點日常工作、升級及故障處理，再用必要實驗驗證。

最新目標校正 · 以此為優先

少部署單元，是否真的少人工作業？

SQLite 隨 Web 部署，可能省去獨立搜尋服務的部署、設定、監控、升級與復原責任。但中央 builder、同步、版本校驗與回滾仍需要有人維護；先逐項盤點是否已自動化、是否可重用公司平台。

比較三種帳：DevOps 長期人工作業（主目標）；開發端維護自製工具／adapter（防止負擔轉移）；硬體、儲存與傳輸（可行性及次要成本）。一次性建置工時另列。

每項維運任務記錄觸發條件、owner、自動步驟、人工步驟、實測 active hands-on 時間、等待時間、所需技能與失敗後升級路徑。未知故障頻率保留未知，不能把一次演練推成每月工時。

優先檢查：同步失敗能否自動恢復；壞索引能否保留舊版並回滾；pod／節點重建需不需要人；新增一個備援地點要做什麼；版本升級與定期 DR 演練需要誰介入。Deployment 種類、實例數與中央工作分開列，不把 pod 數當維運工時。

以下資源與引擎矩陣保留為工具箱，不作成本排名或自動執行順序。先盤點維運差異，優先驗證會影響第一版決策的流程；容量足夠即可，不以最低 RAM 或最高 QPS 決勝。

01 · 為什麼要改變研究方向

目前證據指出配置問題，還沒判定引擎輸贏。

既有百萬頁 C：2 CPU／4 GiB，在每秒 4 次一般 Web 搜尋加每秒 1 次閱讀時，閱讀 P95 約 818 ms，超過研究門檻 500 ms。沒有 API consumer 也會競爭資源。另一輪的版本更新沒有完成啟用。

K4 查詢分解顯示兩段 SQL 都昂貴；不能只移除 count 就宣稱解決。較大資源、專用引擎、另一種索引生命週期，都值得檢驗。

以上是短時、合成語料、特定配置結果。Web 證據 · 更新證據 · 查詢分解。不把歷史數字直接拿來做新引擎速度排名。

原配置 2 CPU／4 GiB；候選 4 CPU／8 GiB。worker 數在開跑前固定；若同時變更，結論是「部署配置比較」，不是單純 CPU 的效果。

省下與新增什麼？

可重用現有 adapter、版本包與讀取鏈。但 SQL、worker 排程、雙版安裝與故障復原仍由團隊維護。更多 RAM 不保證昂貴查詢更快，更多 CPU 也需要足夠併發利用。

B 參照｜保留 ES

假說：專用搜尋引擎可能在相同總額內提供較好的服務能力，並減少自行維護搜尋核心。

Next + adapter → Elasticsearch
↓
異地 MinIO 正文／附件

先用全路徑 2 CPU／4 GiB；若不合格且原因值得擴容，才評估較大配置。

為何仍不等於完整 A？

A 是原 Next + Backend + MariaDB + ES + MinIO 全套。這個分支只測搜尋服務路徑；公司 Backend、DB 備援與既有部署自動化成本尚未取得，不能用 B 的成本冒充 A。合成 ES mapping 也不等於正式搜尋行為。

Pagefind｜集中建置、分地使用

假說：把重工作集中到 producer，可能降低每個備援站點的常駐負擔。

中央建置 → MinIO 索引包
↓
Next 內 server reader + metadata mapping

先做 server 能力檢查與有上限的十萬頁建置；通過才進百萬頁。索引不公開給瀏覽器。

為何重新納入？

舊十萬頁失敗是特定建置寫出階段超過 6 GiB 護欄，沒有產出 reader 測試結果。小型 server API 曾可用，但中文命中與 highlight 差異、fragment mapping 與版本維護成本仍需回答。

歷史證據審查。官方 Node API 是建置介面，不能據此推定 server 查詢整合受到同等官方承諾。

假說：以原生搜尋 API 和索引切換，減少自製搜尋與版本管理程式，值得交換一個獨立服務。

先做小型 API／中文／篩選／權限與版本能力檢查，尚未進百萬頁壓測。

選入理由與限制

官方文件提供磁碟映射儲存、搜尋 filters 與原子 swap-indexes；這是技術機制，不是本專案效能證據。原子切換引擎索引也不會自動保證 MinIO 內容與 metadata 同版。

預設 matchingStrategy 會放寬詞條，結果數也有估算／分頁上限；需先固定語意。磁碟映射的 page cache 仍計入資源，不能只看 heap。

儲存說明 · 搜尋 API · 索引切換

Typesense 為什麼先留備案？

它也是值得考慮的原生 API 引擎。官方描述搜尋索引常駐記憶體，重新啟動會從磁碟重建記憶體索引。先前據此暫選 Meilisearch；使用者已澄清 DevOps 工時優先，故該選擇只保留為候選，需先比較維運責任，不能僅憑 RAM 模型排除 Typesense。若 Meilisearch 的能力或運作方式不合適，且 Typesense 有明確對應優勢，再開新卡。

Typesense 資源需求 · 啟動行為。廠商範例 QPS 與 RAM 比例不作我們的容量證據。

03 · 公平比較

同樣的使用任務，同樣的總預算。

站點預算包住：Next、搜尋程序／workers、必要 metadata、adapter，以及更新期間的新舊版本重疊。
另列共同成本：MinIO、網路與儲存、中央建置／發布、身份與 ReBAC 整合。

研究配置提案：R0 = 2 CPU／4 GiB；R1 = 4 CPU／8 GiB，swap 關閉。ES heap 不等於全部 RAM；其他引擎的 cache、子程序與映射也不能漏算。ES 官方記憶體說明。

先對齊哪些功能？
  • 同一來源資料，title／正文／PDF-only 文字、中英與技術碼。
  • Space、Tags AND、server 授權、pageId 跳轉、正文與附件版本一致。
  • 未授權資料不得出現在結果、總筆數或 snippet；身份未知須拒絕。
  • 排序不強求每筆與 SQLite 相同；必要命中、誤漏找案例與語意差異須可見。
  • 精確 total 是目前研究契約，正式必要性未知。估算或截斷必須另列；不能少做工作卻聲稱同能力比較勝出。

現有百萬語料的 PDF marker 同時在正文，因此需另補真正只出現在 PDF 抽取文字的案例。共用閱讀／附件鏈可重用證據，新 provider 的 mapping／filters 不可直接繼承通過。

04 · 最小而完整的驗證順序

同時準備，重負載依序執行。

  1. 先對齊小型能力與環境。固定版本、配置、來源、判定方式；核對本機可用 CPU／RAM／磁碟。Pagefind 建置的 CPU、RAM、時間與磁碟護欄開跑前另卡固定，中央預算不直接套站點額度。
  2. 首波比較 C-R1 與 ES-R0。用新共同 harness 做一小段 C-R0 對照，避免跨日歷史數字排名。先一般 Web 搜尋與獨立閱讀。C-R1 對 ES-R0 是不同預算的配置取捨，不作同額勝負判斷。
  3. 能維持 Web，才加入 consumer 與更新。各候選用共同到達率，不能在各自不同的最高負載下聲稱公平。必要時加入下載背景；記錄傳輸、校驗、啟用、舊版保留與回滾。
  4. 有資格才增加候選。Pagefind 先十萬頁有界建置、通過再百萬；Meilisearch 先小型能力。失敗保留，不能無限加預算到成功。
研究門檻與停止條件

沿 K3：先每秒 2 次搜尋＋1 次閱讀，合格才到每秒 4 次搜尋。搜尋 P95 ≤ 2 秒；閱讀 P95 ≤ max(合格閱讀 baseline 的兩倍, 500 ms)，baseline 本身須 ≤ 500 ms；失敗 ≤ 1%。30 秒階段只作配置篩選，非正式容量承諾。

資料／授權錯誤立即停；資源／deadline 超標保留失敗。搜尋合格但更新不成功，不能說第一版已完成。只在結果可能改變決策時補測，不展開所有引擎 × 所有資源 × 所有負載的全排列。

05 · 結果如何改變選擇

最後交付的是可選配置與責任，不是一個跑分冠軍。

若 C 擴容就足夠

比較每站多出的資源，是否值得交換較少的遷移／改寫。仍需算自有 SQL、更新與復原責任。

若 ES 同額就更好

降低繼續自製搜尋的優先度；進一步核對完整 A 的增量成本，以及團隊既有 ES 維運資產。

若 Pagefind 站點便宜

再看中央建置、傳輸物件、server 整合與中文差異，是否抵銷多站點常駐節省。

若 Meilisearch 少客製

比較新增服務的部署／升級／還原工作，是否比自己維護搜尋及更新生命週期少；功能降級明列。

成本分三帳：一次性實作與遷移；中央每次建置／發布；每個站點的常駐、更新及演練。觀測時間與資源實記，團隊人時／金額未知就留未知，不用 agent token 代替正式維運工時。

最低可行流量尚未由需求方確認，因此先報「這個配置可完成哪個工作點」，不選出無條件最優解。
