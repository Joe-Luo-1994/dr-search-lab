# 目標校正：DevOps 維運工作量優先

使用者補充：硬體資源不是首要研究目標；核心是 DevOps 日常需要花多少工維護。較少 deployment unit（例如當前 SQLite 與 Web 一起部署）是值得驗證的降成本假說。這延續整體維運成本的原目標，不是新增一個性能目標。

## 決策順序

1. 必要搜尋、閱讀、下載、授權與版本一致性成立。
2. 在可接受資源下通過足夠容量；不以最低記憶體或最高 QPS 為主要勝負。
3. 比較 DevOps 持續人工作業、故障定位與復原、升級、演練及每新增站點的負擔。
4. 分列開發者維護自製工具的責任，避免把工從 DevOps 移到開發團隊就當整體節省；一次性開發／導入與長期維護分開。
5. 硬體、儲存、網路成本另列，在可行性或預算受限時才成為主決策因素。

## 最小維運盤點與證據

| 任務 | 要觀察的證據 |
|---|---|
| 日常快照、同步與健康檢查 | 正常流程是否需人工；失敗告警能否定位到可操作原因；重試是否自動 |
| 索引損壞、更新中斷、版本回滾 | 是否繼續提供舊版；需幾次人工操作；是否需作者直接改 DB／程式 |
| pod／節點重建與冷啟動 | 自動回復及資料取得；需人工解鎖／重建／調參的步驟 |
| 新增異地站點 | 可重用模板、祕密／網路／權限設定與驗收；每站新增工與中央一次性工分開 |
| 升級、修補與 DR 演練 | 版本耦合、測試範圍、備份還原程序與 on-call 所需技能 |

每項記錄 owner、觸發頻率（未知可留空）、自動／人工步驟、active hands-on 分鐘、wall-clock 等待、重試及升級求援。Agent 操作時間只能作實驗資料，不能等同團隊 DevOps 工時；token 不能代替維運成本。首次可由 agent 按 runbook 演練找缺口，真正可交接性需非作者／團隊驗證。

Deployment unit 的種類、站點實例數、中央 producer／排程與平台共用依賴分開盤點。單一 Web deployment 搭 SQLite 可能減少獨立搜尋服務責任，但未證明所有同步及更新工作都消失；ES 若已有公司標準自動化，其增量維護也可能低。兩者均保留假說，不預設勝者。

## 對上一版研究設計的影響

- 資源／引擎比較仍有價值，但成為可行性檢查與成本佐證，不再主導研究排序。
- 先以現有 C 程式與證據列出維運責任／缺口，再盤點 ES 可重用的實際自動化；公司未知不自行補零。
- C 擴容與 ES 同額基準保留。能力與容量足夠就可停止，不為跑分追加無決策價值的調參。
- Pagefind 保留集中建置、多地 reader 假說；需算 builder／server adapter 維護。
- Meilisearch 暫選理由中的 RAM 模型不足以作主要選擇依據；先核維運收益，再決定是否實作。Typesense 不因記憶體模型直接淘汰。
