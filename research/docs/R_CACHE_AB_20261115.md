# 第一版方案的下一步：R 快取對照結果

2026-11-15。已單次完成三組配對。**把 SQLite cache_size 建議值從 16MiB 提高至 64MiB，未讓這份一萬頁合成資料的完整遠端搜尋在 4.8 秒內完成。先停止這項快取調校，將 SQLite 路線的驗證重心轉回完整下載後本地查詢。** 這是研究優先序，不是已選定產品架構，也不是純遠端讀取在所有實作下不可行的結論。

## 本輪要支持的決策

使用者確認：第一版應先說清楚滿足基本需求的能力、效果及成本，再用實際操作與對口討論驗證假設。既有旅程是需求提案，不是所有數字都已鎖定。技術實驗的價值，在於提供遇到需求變化時可用的選項，而非持續追逐某項局部指標。

因此，本輪不修改既有 Spec 或追溯改判歷史失敗。沿用 4.8 秒僅為快取對照；2 秒延遲、負載、更新透明度及更強依賴故障範圍，仍保留為可談的承諾。唯讀搜尋、閱讀、下載及正確授權是主線；正式搜尋 API／ReBAC 契約仍未知。

## 證據與解讀

固定來源、SQL、oracle、工具及七步前綴；先跑一組本地 L 控制，再以 AB／BA／AB 跑三組 R 配對。A=16MiB、B=64MiB；每組皆是新 reader 和新目錄，同一 MinIO release、無 hydration。PRAGMA 回讀確認設定；不等於量到了 SQLite 實際 cache 使用量。資料庫為 22,724,608 bytes，64MiB 大於整份資料庫，不外推百萬頁。

| 組別／設定 | 完整 target | 計數階段 | 中止前 count/rank 相同 path＋Range 重讀 | reader 取樣 RSS 峰值 |
|---|---|---:|---:|---:|
| L 本地／16MiB | 正確完成，10.39ms | 7.29ms | 0 | 114.9MiB |
| 配對1 A／16MiB | 4.8s deadline | 3483.90ms | 1275 | 331.4MiB |
| 配對1 B／64MiB | 4.8s deadline | 3345.70ms | 1418 | 338.9MiB |
| 配對2 B／64MiB | 4.8s deadline | 3316.07ms | 1449 | 338.4MiB |
| 配對2 A／16MiB | 4.8s deadline | 3323.72ms | 1415 | 354.1MiB |
| 配對3 A／16MiB | 4.8s deadline | 3297.89ms | 1450 | 369.6MiB |
| 配對3 B／64MiB | 4.8s deadline | 3292.73ms | 1464 | 366.8MiB |

六組 R 都完成 count，rank 有開始、無結束；完整 target 沒有回傳，不能稱這六次完整輸出正確。七組前綴均符合既有獨立 corpus/body/media oracle；所有成功搜尋輸出另從原始紀錄逐欄位對照 L。rank 未完成時間記 null，不當 0。L 的 10.39ms 不含下載、啟動或整體 DR 恢復。

事前定義的「三組 B 均正確完成，重讀降低至少80%、完整耗時改善至少20%」未成立。這是局部假說辨識門檻，不是產品 SLO。兩個設定都在固定期限中止，觀測工作量不同；**不能用 B 重讀數較高斷言 B 更慢或導致更多總工作**。現有結果僅支持：此設定變更沒有排除觀測到的重讀，也未解決本卡逾時。尚未區分 SQLite/VFS cache、LTX 布局、Space 查詢與 I/O 各自因果，沒有宣稱 page cache 設定被內部忽略。

RSS 包含 reader 的 native runtime，排除 OS page cache，取樣並非硬上限；沒有觀察到可穩定歸因的「固定增加48MiB」代價。設定值不是程序用量。每組均使用相同新增取樣位置，週期500ms；早於期限約0.27ms的單次 timer 回呼保留原值，不包裝成精確4800.000ms。

## 第一版提案如何利用這項結果

這裡的 L/R/H 是 SQLite 的 artifact 讀取策略，與「ES 或 SQLite 搜尋引擎」是不同層次的決策。

| 可帶去討論的路線 | 希望換到的效果 | 明確代價／限制 | 下一步定位 |
|---|---|---|---|
| SQLite L：完整下載可重建本地 artifact，再啟用 reader | 查詢不必逐段跨物件服務讀索引；本地讀取及下載校驗已有有限證據 | 每 reader 完整副本、下載/hash、staging與新舊版空間、發布/回收責任；附件與遠端正文配置須另列，不可偷帶離線保證 | **SQLite 第一版驗證主線**，先把容量、恢復時間及完整流程的成本量清楚 |
| SQLite H：VFS 開始服務並背景補齊 | 嘗試縮短等待完整副本的時間 | 補齊前搜尋可能慢；補齊進度、I/O競爭、失敗與 ready 判準增加維護。小 smoke 成功不代表百萬期間可用 | 在 L 啟動等待確有問題時，作有界備選 |
| SQLite R：純遠端按需讀取 | 減少預先下載的要求 | 目前10k特定查詢已重複逾時；只增加 SQLite cache 無法解決，需更多工程研究 | 暫停快取調校；若「不能完整下載」成為重要限制，再重開讀取布局研究 |
| ES 參照路線 | 保留較接近既有查詢系統的實作路線與搜尋餘裕參照 | 搜尋服務部署/資料/升級/恢復成本；仍須補內容、授權及版本鏈，未證零 consumer 改動 | 保留共同旅程與成本參照，不因這個 R 反例直接選或淘汰 ES |

舊雲端研究中，本地 SQLite 曾在百萬合成短工作集完成，但搜尋分段 P95 約2.45秒，高於暫定2秒；這是歷史不同環境的證據，**本輪未重驗**。MR1 百萬副本約2.133GB、下載/驗證與新 reader 的有限恢復證據，也不能當真實資料量、最低 Pod 規格或公司 RTO。本輪不足以宣稱 L 比 ES 總維運更便宜。

接下來最值得驗的是：在本機足夠空間下，以同一份明確版本的百萬合成來源，量 L 從空副本到第一條搜尋→閱讀→下載鏈的時間、後續搜尋分布、磁碟/記憶體/網路與新舊版重疊成本。先查原 E1 卡與來源可重用程度，只有 L 的等待成本確實影響提案時才擴到 H；不為維持候選數而重跑 R。若新卡不沿用原三候選矩陣，另立版本並保留原未執行狀態。

## 可協商的假設與帶回對口的選項

- **搜尋等待時間**：保留2秒為體驗靶點；量出可達分布後，提出「接受較長等待／限制流量／增加資源／改路線」及各自證據。現在六次 deadline 只有下界，不能承諾放寬到5秒或10秒就能用。
- **冷啟動與本地空間**：完整下載、平時預熱副本、背景補齊是不同成本組合。先量數據，再請 Infra 決定可提供空間及可接受啟動時間。
- **更新中的舊連結**：現有跨 reader 409 是已知缺口；可以提出「透明續行」與「可辨識地重搜/重試」兩種承諾，列清產品與 consumer 代價，尚未替對口接受後者。
- **物件來源額外失聯仍可用**：是比原站故障更強的服務範圍。依已知前提先提核心版本，另列完整必要內容本地化的成本；不把強範圍自動升成第一版必要條件。

以上沒有需立刻打斷研究詢問使用者的缺口。涉及公司資源承諾、consumer 行為或權限政策時，帶具體選項再決策。技術上「做得到」與對口「足夠好」分開驗收。
