資源觀察：更新的成本看得見

Reader 記憶體取樣峰由 mixed-32 的 475.8 MiB，到 update-mixed 的 833.2 MiB；資料包含 file cache，不能只看 Node RSS。

MinIO 本輪 memory.events.max 增加 589，出現回收壓力；OOM=0。累積 kernel peak 516.1 MiB 包含前置發布，曾略高於設定512 MiB，不能解讀成記憶體寬裕或全程嚴格低於設定值。io.stat 不可用，沒有 block I/O 實測。

把每次重做，改成每個版本準備一次

來源合成資料 → SQLite／metadata／物件身份 → MinIO。正式 MariaDB 匯出尚未接上。
每個地區接收版本
異地 MinIO · 1 CPU／512 MiB

啟動／更新下載搜尋包；閱讀／下載按需取件
Next ＋ SQLite workers · 合計 2 CPU／1 GiB
兩個長駐 worker；metadata與摘要按命中讀取；queue 16。下載最多4件同時處理，每件上限8 MiB，先完整校驗後交付。
Web／consumer：搜尋 → pageId → 閱讀／下載

Space／Tags AND 與 canonical page→media 檢查仍存在；身份使用合成 mock。正式 SSO／ReBAC、consumer 契約與實際 editor 尚未整合。

本地資料庫仍包含搜尋全文與 FTS，不是只有很小的 index。V1 318.2 MiB；不能把「正文從 MinIO 交付」解讀成「本地沒有文字副本」。

03 · 更新時還能不能服務

舊版服務，新版下載驗證後啟用

V2 實際下載 318.3 MiB，以應用層上限16 MiB/s控制觀察窗；下載 19.9 秒，下載開始到啟用 20.4 秒。 此時間不是 RTO，也不是跨國網路模型。

smoke 另用受控 hold 驗證 V1 在途請求跨 V2 啟用後仍回正確舊資料；新送舊URL回409，需要重搜。正式測試關閉hook，自然跨啟用請求觀察到 0 筆，並非零中斷保證。

新舊兩份本地 DB 約 636.6 MiB，不含程式、logs與MinIO。更新時的新pool、下載校驗、file cache都受同一reader限額管理。

04 · 用哪些成本換到

服務較少，新增責任仍要有人維護

中央 builder／publisher兩版合成資料建置 8.2 秒，builder RSS峰 514.1 MiB；發布／讀回 5.7 秒。發布程序 RSS峰 1,327.5 MiB，因目前完整讀入資料包並讀回校驗；這是中央工具需維護的成本，不能省略或算進reader。這些是本機一次觀察，不是人日／正式每日工時。
每次完整版本的流量新 DB 約 318.3 MiB／reader／次；每日、每4小時或Pod重建次數會改變總量。正文與附件另外按實際取件計；本輪記的是邏輯bytes，不是WAN帳單。
我們新增的服務程式schema與正規化、長駐worker／queue、下載背壓、版本pin／排空、安裝完整性與磁碟護欄。Kubernetes排程、GC、告警、IAM與正式資料整合仍缺。
實際遇到的操作成本Linux依賴準備；WSL閒置會關閉服務，增加限時supervisor；reviewer要求取消、啟動deadline、摘要oracle與更新探針。原失敗及所有smoke保留。

05 · 這份證據支持什麼決策

可帶具體容量候選討論，還不能宣稱比 A 省

  • 若團隊需求落在這份合成負載範圍，可把這組配置作為下一步正式整合候選。
  • 若要求大量大於8 MiB附件、Range、長期高流量、全部冷資料讀取，需要另定交付策略與容量驗證。
  • 若既有A部署／備份已高度自動化，C新增adapter與發布維護可能抵銷節省。
  • 正式搜尋品質、PDF-only抽取文字入本輪新builder、ReBAC／consumer相容與公司成本仍未知。
