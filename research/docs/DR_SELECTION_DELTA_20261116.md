# A／C 選型：只研究會改變決策的差額

2026-11-16。使用者確認修正研究順序：先比較方案，不先把 C 產品化完成。取代 O1 報告的「下一步先深入舊版服務政策」建議，歷史實驗與結論不回寫。

入口：[手機決策頁](DR_SELECTION_DELTA_20261116.html)。本輪是既有證據盤點與對口操作卡，沒有新容量或復原實驗。外部對口尚未回覆，也未代為發送。

## 本輪結論

**保留 A 作完整可行基準、C 作有受控容量證據的替代候選。下一步最有價值的是核對 A 的既有自動化與增站實際工作，不是再補 C 故障矩陣。** A 公司部署與 runbook 目前未取得；本 repo 的 compose 是搜尋引擎 Demo，不能代替完整 A，也不把 B 的實驗算成 A。

A＝Next＋Backend＋MariaDB＋ES＋MinIO；C＝Next＋SQLite 本地 index／metadata＋異地 MinIO 正文／附件。身份、授權與必要資料仍要處理；C 未接正式 ReBAC。此比較同時改了應用層與搜尋層，不能將所有差額歸因 SQLite vs ES。

### 共同驗收、不同實作

共同工作假設沿用：本地 fz1/fz2 都不可用的 read-only fallback；搜尋、閱讀、下載；每日同步一次為初步目標，非已證 RPO；恢復約一小時為討論目標，非限制 DR 服務時長；可先使用異地 hostname。中文／英文、title/content、Space、Tags AND；正式 consumer 與品質未知。

容許資料年齡、權限漂移、同步失敗是否容許舊版，都是共同政策，先保留待定。不能強制 A 使用 C 的 approved／manifest 協定，也不能要求兩方案共享這個特定故障。以「下一批資料未能完整取得時，使用者可看到什麼／操作員如何定位恢復」比較相同結果。政策若使某方案無法滿足必要結果，才提早升級研究。

## 差額帳（不填虛構人時）

| 責任 | A：可重用假說／未知 | C：目前證據與新增責任 | 歸因及會改選的答案 |
|---|---|---|---|
| API、閱讀、附件及授權 | 既有 Backend 邏輯可望沿用；異地仍需驗身份與依賴 | 需 Next adapter、page→Space／media membership、正文格式／consumer 整合；合成子證據，非正式相容 | 移除 Backend/MariaDB 的代價，B 也可能有。若需重建大量產品邏輯，偏 A |
| 搜尋與行為 | 既有 ES mapping/query/indexing 可望沿用；配置與插件／版本能否搬遷未知 | SQLite schema／文字前處理／FTS 查詢／排名／摘要維護；正式中英文品質未知 | 換引擎差額。必要品質無法達成，或持續修補成本抵銷淨省，才偏 A，或另評 B；不把可討論的語意差異全當必須相同 |
| 每日資料更新 | MariaDB、ES、MinIO 的既有備份、還原或同步流程及一致性未知 | 中央匯出、建索引、發布、每 reader 安裝；K5 更新通過，O1 重啟選版通過，兩者尚未整合 | 同為更新責任，實作不同。A 若成熟自動化已覆蓋，C 不可用「每天一鍵」宣稱勝出 |
| 每站服務與復原 | 增加完整 stack 的模板、stateful 儲存、監控、補丁與 owner；實際增量未知 | 少 Backend/MariaDB/ES 服務種類，增加本地 DB／worker／版本 cache 生命週期 | 無常駐 ES 不等於少同等人時；平台共用工作不要重算每站全額 |
| 容量與競爭 | 未在本 repo 量完整 A，不填零、不套 B | K5 reader 8CPU/12GiB/8workers，MinIO 另配4CPU/4GiB，在百萬合成工作點通過；非全系統成本、正式負載、最低配置或長期保證 | C 可保留候選；不能推導相對 A 節省。只有資源差足以翻轉預算，才優先做可比容量對照 |
| 跨站與共用成本 | 模板／備份平台可能中央共用；各站實例與例外另計 | builder／格式維護可中央共用；每 reader 下載、磁碟與故障處置仍存在 | 站點多不自動使 C 贏：共享成本、每站淨增量、平台階梯擴容分列 |

MinIO／ReBAC／DNS／觀測／演練列為兩者都需考量的責任，但只有需求、配置、owner 與增量相同的部分才能相消。不要一律刪掉共同成本，也不要全部算 C 獨有。

## 三張操作卡：帶給平台／維運核對

目的不是請對口設計 C，而是核對以下 A 可重用假說。每張先選「既有自動化可覆蓋／需要補一段整合／需新增主要機制／未知」，附最小證據連結及缺口。禁止以選項數量加權排名。

### 1. 新增一個異地站點（第一優先）

**給定情境：** 既有公司程式可用，要新增一個同需求 read-only DR 站點，完成身份與 search→page→media 任務。站點機器大小暫不要求估精準值。

**待核對提案：**「A 可沿用部署模板及備份工具，主要補站點參數、網路／secret、restore 與驗收」。請逐步指出真實工具或最近相似站點紀錄；如果某步其實要新寫，標明範圍。不要求交付秘密值。

**最小輸入：** 一份去識別部署／還原 runbook 或 IaC 入口；哪些原已自動化、哪些需人操作／找誰；適用單站還是中央平台。若有歷史操作記錄，分 active hands-on 與等待；沒有則保留未知。

同一份走查另記一個常態維護期間：版本／安全修補、監控調整、演練的正常與例外工作、發生頻率範圍及 owner。只核已有工具或記錄，不要求新增演練；避免只看首次部署而漏掉日常維運。

**C 對照：** 拿掉三種服務，但正式匯出／adapter／發布與部署整合尚缺，不能說只剩配置。若 A 主要是已驗模板且 C 尚需長期客製，優先減少 C 產品化投入；若 A 必須逐站新建維護機制，C 的集中產製值得繼續評估。

### 2. 每日同步一次（同次討論，按需展開）

**給定情境：** 一批 page、Space/Tags、PDF 抽取文字與附件更新後，異地使用者完成搜尋、閱讀、下載。各方案可用自己的恢復／索引方式，結果不可互相矛盾。

**待核對提案：**「A 的現行備份／索引流程可以延伸到異地，不需日常人工作業」。請出示 job/runbook 與成功判定，說明 DB、ES、MinIO 哪些已涵蓋，哪些未涵蓋；沒有就標未知。

**C 對照：** K5 證明受控更新可服務混合流量，O1 證明重啟可選批准版本；不是同一套完整生命週期。排程、正式資料來源、告警與 GC 仍需 owner。頻率增加不自動等於人工倍增。

### 3. 一次更新失敗，交給非作者處理（先用既有紀錄，不注入故障）

**給定情境：** 新一批資料尚未完整可用；對口說明使用者看到什麼、如何發現／定位、重試或恢復。可以是 A 自己的失敗型態，不強制 approved hash mismatch。

**待核對提案：**「既有告警與 runbook 能定位到可操作原因，不需原作者改程式」。請給既有演練或 incident 的去識別紀錄；若無紀錄，僅列操作假說，不能標驗證通過。

**C 對照：** O1 壞 pin 拒絕啟動且保留 cache；自動重試／告警／恢復沒驗，K5 fatal worker 復原也未驗。先比較所需自製機制，不立即補齊。

## 明確改選與停止條件

- A 的增站／更新／復原有可重用證據、增量低：偏 A，停止把 C 全面產品化；C 保留為研究備案。仍需檢查同 DR 要求，不能只憑「有 Helm」判定成熟。
- A 有明確逐站人工負擔，C 的共用維護有 owner 且需求差距可接受：保留 C，再只驗最可能吃掉節省的那一項。這是投入條件，不是已證 C 較省。
- C 的必要 API／搜尋／授權行為無法達成，或客製整合與長期維護成本抵銷每站淨省：偏 A；有客製本身不足以淘汰，仍需按差額比較。若問題只在搜尋引擎，可考慮 B，但 B 保留應用轉接成本、要獨立證據。
- A 資料依然拿不到：結論維持條件式，不做完整 A 模擬來冒充公司成本，也不以更多 C 實驗填這個未知。

下一行動是一次有證據的 A 增站 runbook 走查（操作卡1），卡2/3作輔助。本機這輪已做到：彙整最新 C 證據、形成差額帳與具體對口提案。待確認的公司輸入無法從本機合成實驗取得；暫停新 benchmark、引擎矩陣與舊版政策故障展開。研究停止條件是足以選方案，不是 C 功能補齊。
