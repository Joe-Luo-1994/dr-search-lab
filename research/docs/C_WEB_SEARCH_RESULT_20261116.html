沒有 API consumer，Web 搜尋仍會影響閱讀。

上一輪Web只用唯一詞與已發布文件關鍵字，不能代表一般搜尋。本輪將常見詞、中文、Space、Tags等九種查詢放入Web所需的伺服器任務。

固定 2 CPU／4 GiB；沒有 API consumer、附件負載或更新，也沒有加資源。搜尋與閱讀仍共享兩個SQLite workers。
實際結果競爭在哪裡如何改變決策證據與限制

01 · 先看任務

搜尋的人與閱讀的人，會互相影響嗎？

一個搜尋任務是「開頁SSR → 搜尋 → 收到且驗對結果」，另有獨立使用者每秒讀一次已發布頁。搜尋任務不是使用者人數，每次都重新開頁也不同於已開頁後反覆輸入關鍵字。

正式210個搜尋任務、120個獨立閱讀全數完成；容量門檻失敗指等待太久，不是HTTP錯誤。每秒1個搜尋時仍有單次約2.30秒的慢例，P95合格不代表每次都在2秒內。

02 · 架構怎麼解釋

限制來自共同的工作，不是呼叫者叫什麼。

Web搜尋：SSR開頁＋一般查詢
Web閱讀：獨立SSR取正文
API consumer：0
↓
同一Next reader：2 CPU／4 GiB
共享queue → 兩個SQLite workers
page metadata與搜尋競爭相同執行名額
↓
百萬筆本地搜尋資料（3.313GB）
正文從MinIO取回（獨立4 CPU／4 GiB）

最後一階reader平均 1.9 核等值，pool觀察排隊最多3，Next event-loop最大觀察延遲22.1ms（量測解析度20ms）。這些是定位線索，不是完全隔離變因的根因證明。

本輪合成契約包含exact total；正式需求尚未知。現碼每次搜尋會計算exact total，再取BM25排序Top10，並套Space／Tags條件。Web和consumer都付出這些工作；只隔離consumer不能保證一般Web查詢便宜。

03 · 這會改變什麼決策

先弄清搜尋成本，再決定花在哪裡。

8GiB更新備案暫緩；K2更新失敗仍未解。現在需要先衡量一般Web搜尋能否接受，以及改善需要多少自有程式責任。不能以「DR沒有consumer」排除容量風險。

  • 下一個最小技術診斷：分開量exact count、篩選、排序Top10的成本，保留原回傳契約與結果；先定位，還沒有批准取消total或降低搜尋品質；目前沒有查詢內部分項時間，不能先認定count是主因。
  • 同契約改善：若SQL／索引有可修正的浪費，修正後用相同案例重驗，與多給CPU或獨立搜尋服務的成本比較。
  • 需要妥協時才討論：近似／不回total、查詢限制、限流或延後顯示，均是待決策方案，不默默當成使用者接受。
  • 保留A：若維持基本Web需求需要很多自有排程、查詢與更新機制，應回頭算既有Backend＋ES異地部署的增量成本；目前未做A同條件測試。

本輪新增的是研究runner／驗證與報告，沒有新增產品部署元件或硬體配額；實際工程人時、token金額及公司infra單價未知。

04 · 可以相信到哪裡

功能成功與容量合格分開看。

百萬頁實際表單的五種文字查詢已顯示預期結果：常見詞、唯一詞、中文、無結果、已發布文件marker。現有Demo沒有Space／Tags／身份控制項；正式九種shape透過HTTP模擬Web所需能力，沒有宣稱完整UI可操作或量到瀏覽器渲染。

無結果目前只是空列表，清楚的空結果提示仍缺；本文不將agent操作成功當真人體感驗收。每次搜尋後不點未發布的長尾文件，閱讀只驗p000001熱頁；不代表百萬文件交付閉包。正式ReBAC、真實分布、ES品質／排序相等與公司流量皆未知。
