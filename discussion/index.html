01 · 目標與使用任務

首先，災難時要能完成什麼？

假設台灣 fz1／fz2 都不可用，但使用者仍可連上異地 cluster；公司 ReBAC 另有足夠備援。使用者與 consumer 只需要搜尋、閱讀、下載，不提供寫入。

目前工作假設：每天同步一次；約一小時恢復是討論目標，尚未量得端到端 RTO。DR 沒有一小時的服務期限。可先使用異地 hostname，切換政策後續與 infra 對齊。

機制與實際反例

遠端內容實驗 37／38 頁，17 組／40 次 API 請求通過；本地搜尋，授權後按版本化 key 從真 MinIO 讀正文／PDF，核 hash。錯物件、跨 page media、撤權／未知權限有拒絕證據，但身份與 Role 是合成的。

MinIO 停止時，已安裝 reader 的搜尋仍可用，正文／下載明確失敗；空 cache 無法安裝啟動。復原後能再次讀取。這不是全站離線可用，也不是正式 HA。

小 PDF 下載已驗；這輪 iframe 視覺預覽未驗收，大 PDF／Range、公司 editor 與正式身份仍未知。任務鏈與反例／獨立審查

每天更新，重啟後仍能服務

兩段機制各有子證據尚未整合成正式生命週期

K5 在混合流量下切換索引並排空舊 worker；O1 另外驗證從遠端核准版本啟動。這是兩個不同 runtime，不能合併寫成同一正式版本全部通過。

授權時效與失敗處理保留什麼？

即時 Space Role 與快照內 page→Space／media 關係的時間不同；移頁或移除附件可能在下一次同步才反映。這是所有方案要對齊的資料／權限政策，不能以「讀 ReBAC」宣稱已消除漂移。

O1 六個小資料案例通過：有舊快取、空快取可依核准版本取得 V2；重用仍核完整 DB hash。壞 manifest pin 回 503，不 ready、快取不變；自動重試／告警／修復後恢復尚未驗。O1 結果與機制

資格判斷：C 已超過純概念階段，可進入導入評估；正式搜尋接受、身份／consumer 整合與完整 DR 演練仍未完成。A 是已接受的可行架構方向，不代表異地部署已由本研究驗收。

本地副本、PVC 與多地重建

C 的 SQLite 搜尋在 Pod 本地執行；MinIO 保存可重取版本。若不用 PVC，Pod 重建後可能要重新下載；既有快取也須驗證版本與內容。需要規劃本地暫存容量、新舊版本／staging 空間、下載時間與清理。

集中建索引供多地重用，避免每個 Pod 重建的 CPU／來源依賴；代價是中央建置與發布鏈。ES 索引也可能從來源重建，不能把「可重建」當 C 獨有優勢。

有現成 API，仍要完成哪些事？

Snapshot repository 可用相容 MinIO，但要驗 repository 相容性與跨區完整性；同一 repository 僅一個 ES cluster writer，其餘唯讀。異地不能依賴災難時不可達的台灣儲存。官方 repository 說明

仍需排程、完整性與還原驗證、版本相容、空間與保留監控。等災難才 restore 要計入 RTO；平時先還原則要平時資源。Alias 只切 ES，不會一起切 MariaDB／MinIO。若應用原先寫死實體 index 名，也要適配。

「A 現在主要剩 ES 移轉」是使用者目前理解，不等於已取得公司完整還原證據；C 的盤點無需等這份證據才開始。

05 · 省掉的與新增的，要放一起看

少一套 ES，確實少一種運行責任；節省多少仍待核。

A · 延伸既有完整服務

可望少做：重建 Backend 邏輯、換搜尋語意、重做 consumer 契約。

仍需承擔：異地資料還原／同步、ES 容量與磁碟、服務升級、儲存維護、監控及事故處理；既有自動化可降低人工，但不把責任歸零。

以新增／可避免成本計，不重算公司早已承擔的全部平台研發。A 真實增量未提供。

C · 集中產製、應用內讀取

可望少做：每站獨立 Backend／MariaDB／ES 的部署與運行管理。

新增／轉移：資料 exporter、搜尋／API adapter、發布格式、worker 與本地版本生命週期，以及測試／故障診斷。

中央工具可多地共用；每站與每 Pod 的儲存、下載、更新、例外處理仍存在。

「都需要備份／告警」不表示成本相同；「服務數較少」也不等於總工時較低。共同依賴只有在範圍、配置、owner 與增量相同時才能相消。
團隊估成本時只填這四欄
  1. 一次性導入：程式適配、部署模板、驗收與訓練。
  2. 中央持續維護：格式／來源／套件升級、共用發布工具、品質回歸。
  3. 每站持續增量：正常與例外人工、修補、容量、演練；記頻率範圍與 owner。
  4. 基礎資源：reader／ES／DB、MinIO、保留空間與跨站／站內流量，分開列。

先記主動操作時間與等待，不強求精準金額；未知留空。若換成費用，用相同期間與費率；別以 agent 執行秒數、程式行數或部署數代填。條件成本試算與未知欄位

06 · 帶條件的提案與備案

先判值不值得導入，再決定補哪項證據。

何時傾向 C？

基本搜尋／consumer 差異可接受；六包有可承擔的 owner；中央新增維護有機會低於多站省下的服務工作。先做最小正式整合與估範圍，再決定正式化。

何時回到 A？

必要行為無法達成、C 改造／持續維護抵銷淨省，或 A 已有低增量的異地自動化。保留現行產品邏輯是合理選擇，不因研究做很多就必須選 C。

如果只是 SQLite 搜尋差距過大，B 可以怎麼用？

B 保留 ES，Next 承接部分應用功能、配合異地 MinIO。它可能減少換引擎的成本，但仍有移除 Backend／MariaDB 的轉接責任。既有小型 ES API 參照只是 B 子證據，不能當 A 的容量與工時。

若問題來自正式正文、授權或 API 的大量產品邏輯遷移，換成 B 不一定解決；應回看保留 Backend 的價值。

為什麼不是 Pagefind？

Pagefind 未永久排除。歷史真 Next 小型搜尋 API 有成功證據；Space／Tags、預抽附件文字不是已知做不到。特定 100k 建置在當時 6 GiB 護欄內未完成，屬 builder 預算失敗，不是 100k reader 失敗或一般能力上限。

中央 builder 可獨立配置資源；Node／browser 的中文結果曾不同，後續小型成功未抹掉此反例。早期 fragment／缺檔依賴有後續修正，不能仍當必然失敗。若它能減少 server adapter／更新／搜尋維護，值得重開；目前沒有相同工作點成本證據支持替換 C。Pagefind 能力與歷史專頁

本次會議只需要形成三個結論

  1. 必要任務與差異：用本報告的搜尋／閱讀／下載範圍，確認哪些是必須、哪些 DR 可協商。避免從「你們需要什麼」重新發散。
  2. C 的落地責任：六包逐項確認可沿用量、要適配／新增的工作與 owner；暫時不能估的明確留未知。
  3. 下一項最有價值的證據：A 的 ES 異地同步及既有自動化、C 的正式整合／品質，哪一項最可能翻轉選型？一次只選最關鍵項，不自動展開矩陣。

A 資料暫缺不阻塞 C 工作盤點；也不以更多 C 實驗代替 A 成本。當合理成本範圍與必要任務已足以選方案，即可停止探索。
