選型主報告Pagefind 為何暫停深入？證據摘要

異地唯讀 DR · 團隊選型討論版 2

先沿用成熟能力，再判斷替換是否值得。

第一版提案優先核對 A：保留既有 Backend、Elasticsearch 與必要資料庫，確認 Gateway 能否在 DR 沿用。SQLite／Pagefind 保留為有條件的替代候選。

推薦方向，不是成本定案：我們尚未證明 C 的總維運成本更低；少部署幾種服務，可能換成更多自行維護的 API、授權、worker 與索引生命週期。先比較 A 的異地新增工作與 C 的淨節省，再決定是否繼續替換。

本輪暫停：Pagefind 上游／引擎優化、新增擴容壓測與 C 全面產品化。保留：全部成功、失敗與可重用成果。

01 · 目標與使用任務

首先，災難時要能完成什麼？

假設台灣 fz1／fz2 都不可用，但使用者仍可連上異地 cluster；公司 ReBAC 另有足夠備援。使用者與 consumer 只需要搜尋、閱讀、下載，不提供寫入。

目前工作假設：每天同步一次；約一小時恢復是討論目標，尚未量得端到端 RTO。DR 沒有一小時的服務期限。可先使用異地 hostname，切換政策後續與 infra 對齊。

找到需要且有權限的文件

合成必要案例有證據正式品質與 API 未驗

搜尋 title／content，選 Space、多 Tags 全部符合；中英文，PDF 已抽取文字可作來源。搜尋結果至少帶 title／pageId，highlight 是加分項。

C 的機制：正式資料需匯出成 SQLite 全文與 metadata；API 依可存取 Space 篩選並回傳結果，media 另驗 page membership。

搜尋效果、ES 差異與證據界線

E1 的 37 頁合成來源，ES 參照 B 與 SQLite C 各 12 題都有指定目標文件的保存回應，涵蓋中文、英文、技術碼、title／正文／PDF、Space、Tags。這不是公司品質命中率。

其中技術碼與 PDF 題，兩者都把詞面相近的干擾頁排第一、目標頁第二；另一題目標都第一，但後續排序不同。ES 不能直接充當唯一品質真值，C 也沒有證明語意等價。

原時間戳驗收與 UI 定位失敗保留；後續有限補驗與離線核對支持合成必要任務結案。未用重跑抹掉原失敗。原結果與案例／補驗裁定

正式驗收提案：用代表性的必要查詢與指定目標文件，檢查能否在約定前幾筆找到、篩選是否正確、consumer 必要欄位是否可用；由團隊約定門檻，不先追求整套 ES 排序等價。品質研究界線

點結果後閱讀、下載

遠端內容任務鏈有證據既有 editor／大檔整合未驗

Web 已有 pageId→頁面／editor 路徑，應優先沿用。C 新增的是搜尋銜接、版本及 canonical 授權；PDF 類 page 還要解析 mediaId，不能只驗 pageId 就任意取檔。

機制與實際反例

遠端內容實驗 37／38 頁，17 組／40 次 API 請求通過；本地搜尋，授權後按版本化 key 從真 MinIO 讀正文／PDF，核 hash。錯物件、跨 page media、撤權／未知權限有拒絕證據，但身份與 Role 是合成的。

MinIO 停止時，已安裝 reader 的搜尋仍可用，正文／下載明確失敗；空 cache 無法安裝啟動。復原後能再次讀取。這不是全站離線可用，也不是正式 HA。

小 PDF 下載已驗；這輪 iframe 視覺預覽未驗收，大 PDF／Range、公司 editor 與正式身份仍未知。任務鏈與反例／獨立審查

每天更新，重啟後仍能服務

兩段機制各有子證據尚未整合成正式生命週期

K5 在混合流量下切換索引並排空舊 worker；O1 另外驗證從遠端核准版本啟動。這是兩個不同 runtime，不能合併寫成同一正式版本全部通過。

授權時效與失敗處理保留什麼？

即時 Space Role 與快照內 page→Space／media 關係的時間不同；移頁或移除附件可能在下一次同步才反映。這是所有方案要對齊的資料／權限政策，不能以「讀 ReBAC」宣稱已消除漂移。

O1 六個小資料案例通過：有舊快取、空快取可依核准版本取得 V2；重用仍核完整 DB hash。壞 manifest pin 回 503，不 ready、快取不變；自動重試／告警／修復後恢復尚未驗。O1 結果與機制

資格判斷：C 已超過純概念階段，可進入導入評估；正式搜尋接受、身份／consumer 整合與完整 DR 演練仍未完成。A 是已接受的可行架構方向，不代表異地部署已由本研究驗收。

02 · 為什麼改變研究順序？

我們要減少總維運工作，替代方案必須證明收益。

研究原本希望用 Next＋本地索引，省下異地 Backend／MariaDB／ES 的維護。但實驗已具體揭露 worker、併發保護、發布／切版、快取、API 與授權適配等責任。這些不是全部新增，也不能只因有客製就淘汰 C；需要辨別哪些原本已有、哪些要重新實作、誰持續維護。

移除 Backend／MariaDB

API 契約、身份、metadata、page→Space→media、正文與附件交付、錯誤處理要由誰承接？這是應用層替換成本。

替換 Elasticsearch

文字分析、搜尋結果、排序、摘要、容量與索引生命週期由誰負責？這是搜尋引擎替換成本。

兩個改動要拆開。保留 ES 卻移除 Backend 的 B，仍有應用轉接成本；保留 Backend、只換引擎則是另一個未驗配置。B 的實驗不能算成完整 A 的容量或維運成本。

不需要先證明 SQLite／Pagefind 完全不可行，才允許停止投入。若替換的可預期收益不足，沿用成熟架構本身就是合理選擇。查看這次調整的判斷邊界

本地副本、PVC 與多地重建

C 的 SQLite 搜尋在 Pod 本地執行；MinIO 保存可重取版本。若不用 PVC，Pod 重建後可能要重新下載；既有快取也須驗證版本與內容。需要規劃本地暫存容量、新舊版本／staging 空間、下載時間與清理。

集中建索引供多地重用，避免每個 Pod 重建的 CPU／來源依賴；代價是中央建置與發布鏈。ES 索引也可能從來源重建，不能把「可重建」當 C 獨有優勢。

有現成 API，仍要完成哪些事？

Snapshot repository 可用相容 MinIO，但要驗 repository 相容性與跨區完整性；同一 repository 僅一個 ES cluster writer，其餘唯讀。異地不能依賴災難時不可達的台灣儲存。官方 repository 說明

仍需排程、完整性與還原驗證、版本相容、空間與保留監控。等災難才 restore 要計入 RTO；平時先還原則要平時資源。Alias 只切 ES，不會一起切 MariaDB／MinIO。若應用原先寫死實體 index 名，也要適配。

「A 現在主要剩 ES 移轉」是使用者目前理解，不等於已取得公司完整還原證據；C 的盤點無需等這份證據才開始。

04 · 證據能支持到哪裡？

容量有風險，卻不能把工作點當作吞吐上限。

候選目前觀察不能宣稱
SQLite／C百萬合成頁，reader 8CPU／12GiB／8workers，通過每秒6次搜尋搭配閱讀、下載及更新的工作點；MinIO另配4CPU／4GiB。6 RPS 是最大容量、正式consumer已可承諾，或比完整A更省。
Pagefind100k中央建置與完整性通過；單個預期50k命中的冷server查詢碰5秒研究截止。D2定位到同步WASM搜尋呼叫邊界未返回。已測得RPS上限、所有query都失敗，或正式SLO就是5秒。
完整 A使用者接受的可行基準；既有產品與自動化可重用量待核。本研究已驗異地完整A、維運為零，或B參照結果可以代替A。

結論：替代方案尚不足以承諾正式 consumer 負載，但也沒有證據支持「兩者只要開 API 就一定撐不住」。負載判斷需要既有 Gateway／BE 的流量、突發、查詢組成及可協商的 DR 服務範圍。

SQLite 的通過與失敗都保留

4CPU／8GiB／4workers 在前六階通過，更新成功但更新期間5/1620任務被拒，閱讀／Web體驗未全合格。8CPU／12GiB／8workers 的七階2550任務完成；更新階1620任務完成，Web搜尋P95約1206ms、consumer約1272ms、閱讀約13ms。這是短時合成工作點，不是最高RPS或正式品質。

9個query等權、256正文hotset／8media、SSR/API而非完整browser資產，正式ReBAC與consumer相容仍未驗；K5熱更新與O1重啟也不是同一runtime的完整生命週期。SQLite證據摘要

為什麼 Pagefind 沒有直接加到8核？

D2查詢內5個樣本約覆蓋4.019秒，CPU約1.006核，沒有觀察到quota throttling、OOM、回收/refault壓力。僅增加Pod核心數不會自動平行化同步呼叫；未來worker併發收益仍可能存在，但那是另一個架構與成本。沒有啟動擴容壓測。

原始落地盤點／A／C 差額與對口操作卡

06 · 省掉的與新增的，要放一起看

比較可沿用的工作與新增責任，不以服務數判勝負。

A · 延伸既有完整服務

可望少做：重建 Backend 邏輯、換搜尋語意、重做 consumer 契約。

仍需承擔：異地資料還原／同步、ES 容量與磁碟、服務升級、儲存維護、監控及事故處理；既有自動化可降低人工，但不把責任歸零。

以新增／可避免成本計，不重算公司早已承擔的全部平台研發。A 真實增量未提供。

C · 集中產製、應用內讀取

可望少做：每站獨立 Backend／MariaDB／ES 的部署與運行管理。

新增／轉移：資料 exporter、搜尋／API adapter、發布格式、worker 與本地版本生命週期，以及測試／故障診斷。

中央工具可多地共用；每站與每 Pod 的儲存、下載、更新、例外處理仍存在。

「都需要備份／告警」不表示成本相同；「服務數較少」也不等於總工時較低。共同依賴只有在範圍、配置、owner 與增量相同時才能相消。
團隊估成本時只填這四欄
  1. 一次性導入：程式適配、部署模板、驗收與訓練。
  2. 中央持續維護：格式／來源／套件升級、共用發布工具、品質回歸。
  3. 每站持續增量：正常與例外人工、修補、容量、演練；記頻率範圍與 owner。
  4. 基礎資源：reader／ES／DB、MinIO、保留空間與跨站／站內流量，分開列。

先記主動操作時間與等待，不強求精準金額；未知留空。若換成費用，用相同期間與費率；別以 agent 執行秒數、程式行數或部署數代填。條件成本試算與未知欄位

07 · 帶著具體方案討論

第一版優先 A；C 與 Pagefind 需要明確的重新投入條件。

帶給團隊的方案：異地維持唯讀搜尋、閱讀、下載，優先延用既有 Backend／ES／必要MariaDB及可用的Gateway機制；以既有部署、備份／還原與監控流程確認增站差額。這是推薦順序，尚非正式採用或成本勝出。

支持優先 A 的答案

現有模板／同步／告警可延伸，API與授權可重用；新增站點主要是配置、資源與少量整合。即使多維護ES／DB，也可能低於維護新adapter與索引服務生命週期。

會讓我們重開 C 的答案

A有明確的每站人工或平台負擔；C在相同必要任務下可量到足以抵銷中央新增維護的淨省，且有owner承接。搜尋差異、consumer負載與降級範圍需有證據及明確接受。

下一次討論只走查一條既有路徑

  1. 實際請求路徑：從search→page→media畫出Gateway、BE、資料庫與授權依賴；每項標可沿用／需適配／新增，以及異地不可達時的影響。
  2. A新增一站：用現有IaC／runbook逐步看部署、同步、更新失敗、容量與升級；記誰操作、哪些自動化、哪些需要找原作者。A仍有ES／DB磁碟、修補與事故責任。
  3. 真實負載基準：取去識別的Gateway／BE流量摘要，看常態、尖峰／突發、query種類和consumer重試；確認DR可協商範圍，再決定是否需要一個可比容量試驗。
