團隊選型報告Pagefind 能力與限制證據摘要

團隊原先期待的方案 · 證據重判

Pagefind 做得到什麼，為什麼還沒選它？

目前不足以排除 Pagefind。它有真 Next.js Server API 與小型任務成功證據；尚缺的是可承擔的規模建置、必要中文行為，以及 server 整合的長期維護成本。

給團隊的提案：把 Pagefind 保留為正式候選，不把 SQLite 的進展當成淘汰它的理由。若要選定 SQLite，可由團隊接受暫不補 Pagefind 比較證據的不確定性，或選擇先補一個有界驗證；不把 Pagefind 必須先跑完當成採用 SQLite 的前提。本次沒有新增建置／壓測。

01 · 為什麼原本值得期待？

集中建索引、多地讀取，不必增加獨立搜尋服務。

這個方向符合降低異地運行負擔的目標。Pagefind 可將內容建成靜態搜尋產物，再由查詢端載入。以本專案來說，問題是如何承接私有內容、Next Server API 與多身份授權，而不只是把搜尋框放上網站。

中央：正式資料／已抽取 PDF 文字 → Pagefind builder
↓ 完整版本與 metadata 發布
異地 MinIO：bundle、正文、附件
↓ 版本化載入／本地資產或 cache 策略待定
Next Server API → Pagefind provider
驗身份／Space／page-media → 回傳允許的結果

這是候選整合圖，非百萬頁已驗部署。Browser→公開全量索引與Server內查詢是不同架構；目前應討論後者來承接consumer與私有內容。

02 · 已能做到的，不再當未知

Server API、篩選與 MinIO，都有具體依據。

Next.js Server 提供搜尋 API

歷史小型實測12 頁真 Next 的第二輪實驗，Pagefind 與 SQLite 各 18/18 任務通過，該輪合計 52 HTTP；涵蓋中英文／代碼、分頁、正文／附件及 mock scope。highlight 當時允許 null。

因此「Pagefind 只能在 browser 跑」不足以作為排除理由；但官方 Node API 的文件主要是建索引，不等於有可直接替代 ES 的正式查詢服務。本研究 server 查詢使用 generated JS／WASM 與 adapter。官方 Node 索引 API

Space、Tags AND 與 PDF 抽取文字

官方能力＋合成案例複合 filter 可表達 Space 與多 Tags 全符合；custom record 可納入已抽取文字與 metadata，不必先有真實 HTML 頁面。這不是 Pagefind 內建 PDF 解析，也不是 filter 自動等於授權。官方 filter／custom record

索引產物放 MinIO

歷史真 MinIO 實測115 物件逐 hash 一致；跨 origin、替換 Web／新 browser、private bucket 經 proxy 的單輪 28 checks／12 queries 成立。

界線：該輪查詢在 browser；不能直接當作 Next consumer API、正式 ReBAC 或完整版本發布全部成立。需要將這些子證據接起來驗收。

一萬頁可建置並完成短 API 工作集

Pagefind 1.6.0／合成來源歷史 10k 建置約 12.35 秒、取樣程序樹 RSS 約 958 MiB，有可用產物與短任務證據。

界線：當時負載窗口很短，不作穩態 QPS 或容量承諾，也不與後來 SQLite K5 直接排名。

03 · 真正遇到的限制

分清建置失敗、搜尋差異與整合責任。

限制一：十萬頁建置超出當時預算

100k ingest 完成後，在 write 階段約 102.85 秒時程序樹 RSS 到 6,505,082,880 bytes，超過 6 GiB 護欄，實驗停止；沒有可用 bundle，所以沒有執行該量級 reader，1M 也未跑。

能說：該版本／來源／設定不符合當時建置預算。不能說：Pagefind 只能搜尋一萬頁、十萬頁查詢失敗，或加資源也不可能。

中央 builder 的短暫資源與每站 reader 必須分帳。較大的集中建置成本可能可接受；但尚未測得需要多少，不能用線性外推填值。

限制二：中文的 server／browser 行為曾不同

同一份 100 頁 bundle，查「資料庫備份」時 Node 1 筆、browser 3 筆，highlight 也不同。後來不同 fixture 的中文成功，不能抹掉此反例。

官方 extended build 有中文斷詞能力，但 server 語言初始化／查詢行為仍需核對。正式要求應是必要文件找得到、差異經接受；不必每個排名都與 ES 一致。官方多語言說明

限制三：靜態產物不代表整合零維護

仍有 generated module 初始化、result ID→pageId／scope mapping、版本資產、cache、失敗隔離、升級回歸。歷史某 adapter 解析 1.6.0 內部 fragment 格式，並使用 SQLite 保存映射；若沿用，不能宣稱所有 SQLite 或格式耦合責任都消失。

早期冷查詢需取 5 個 fragments、缺 Pagefind 產物牽連其他路徑的問題，後來已透過 lazy init／build-time mapping 修正，冷查詢 fragment GET 5→0。應保留修正成果，也計入新增映射責任；不能仍拿舊失敗當必然結果。

限制四：私有全量索引不能只靠 UI 篩選

歷史 browser 初探移除 Space filter 後可讀受限內容；這否定那個授權設計，不否定 server Pagefind。若把全量私人 bundle 發給使用者，不能用隱藏結果當保護；server 候選仍需正式授權與輸出欄位檢查。

04 · 我們比較得公平嗎？

目前沒有證據說 SQLite 全面勝出。

SQLite 後來獲得長駐 worker、更新流程調整與資源擴充，K5 找到百萬合成工作點；Pagefind 較大建置分支仍停在舊 100k／6 GiB 預算。研究投入、來源與任務契約並不對等。

同一歷史 MS1 中，SQLite 百萬頁也因極深分頁超時而未通過完整工作集。後來的成功只能代表後來的範圍／配置，不是對 Pagefind 的同條件勝出。

公平不是直接把 SQLite reader 的 12 GiB 給 Pagefind builder：建置與服務是不同角色，取樣 RSS 與 cgroup 上限也不是同一量測。要比較的是必要能力與整體維運責任。

05 · 若團隊仍期待 Pagefind，下一步怎麼選？

先補一個有界建置驗證，不直接開百萬矩陣。

待討論，尚未執行：在固定、可部署的中央 CPU／RAM／磁碟與期限內，對固定 100k 來源產生可發布、mapping 與 hash 完整的 bundle。先定預算，只跑一個配置；超限或無完整產物即停止，不無限加 RAM。

成功後只補少量獨立來源預期與舊中文反例的 server 查詢確認，再決定是否值得往 reader 容量或百萬建置前進。通過建置不等於百萬查詢通過。

支持改選 Pagefind 的答案

必要任務成立、搜尋差異經接受；中央建置可承擔；provider／更新／版本維護比 SQLite 更適合團隊，且整體維護收益有依據。

支持保留 SQLite 或 A 的答案

必要能力不成立，或 mapping／adapter／建置與升級責任抵銷收益。僅「Pagefind 能 build」或「SQLite 已做很多」都不足以選定方案。
