選型主報告Pagefind 為何暫停深入？證據摘要

替代候選 · 最新狀態

Pagefind 能建十萬頁索引；Server 搜尋仍有未解風險。

保留它的能力證據，也保留高命中首題逾時。目前暫停深入優化，回到「為總維運成本付出這些適配是否值得」。

本版推薦：優先核對沿用A的增站差額。Pagefind仍是有條件備案；沒有永久排除，也沒有正式採用。不是「只能建10k」，更不是已證能承接正式consumer。

01 · 它與 SQLite 候選接近在哪裡？

中央匯出：title／正文／已抽取PDF文字／Space／Tags
↓ 中央建置與完整版本發布
異地 MinIO：Pagefind bundle＋可信metadata，另存正文／附件
↓ Pod下載、驗證與安裝本地版本
Next Server API → Pagefind JS／WASM → 授權後結果／pageId

這是候選整合圖。實驗的本地資產listener只綁localhost；私有全量索引不公開給browser。Server執行時，不能套用瀏覽器替server分擔運算的優點。正式內容仍應走閱讀／下載授權，ReBAC不取代page-media關係驗證。

G1／G2／D1／D2沿舊MS1：正文與metadata仍在本地SQLite，不是「正文與附件從異地MinIO讀」的完整C整合。

02 · 已有能力，沒有抹掉

  • 歷史真Next第二輪12頁，Pagefind／SQLite各18/18，該輪合計52 HTTP；小型server API、中英文／代碼、分頁及mock scope有成功證據，不是正式consumer或ReBAC。
  • Space／Tags AND與預先抽取附件文字有小型依據；Pagefind不負責抽PDF。highlight曾允許為null，正式是否接受仍未知。
  • PF02的115個MinIO物件／28checks／12queries，是browser資產路徑證據，不能當server API已整合。
  • 早期每次hydrate全部fragment的依賴曾改善，12頁冷query fragment GET由5→0；代價包含build期映射與版本校驗，不能說零IO。

歷史與最新來源識別

03 · 十萬頁建置已通過，原先的限制需要更新

100,000頁

4CPU／12GiB／swap0，建置＋完整性驗證約161.139秒；cgroup峰7.915GiB。十萬份mapping／fragment及來源核對通過。

101,571檔

Pagefind bundle約97.75MB；另有約154.44MB SQLite正文／metadata／映射。合計約252.20MB logical，逐檔allocated約608.61MB；不是純索引252MB。

舊100k在6GiB程序樹RSS軟預算中止；新測試為cgroup硬限制，Node也由22.21.1換成本機22.18.0。不能做純RAM因果或最低資源推論，卻足以修正「目前只有10k產物」的證據狀態。

這份包還帶來哪些維護責任？

超過十萬個小檔的發布／下載／校驗，本地版本快取，opaque result ID→pageId mapping，以及Pagefind1.6.0私有fragment格式相依。十萬頁版本仍用SQLite保存映射；12頁小fixture的JSON映射不能證明大規模已移除SQLite。

04 · 失敗發生在哪裡？

G2首題：100k來源，身份可讀50k頁，commonterm預期total=50,000、回10筆。5秒研究截止前未取得HTTP回應；其餘31個必要案例與1個歷史觀察未執行。不是32題全失敗，也不是正式5秒SLO。

D1：pf.search未返回；自有mapping尚未開始
↓ 僅加入內部trace，另跑一次同題
D2：body／解壓／WASM初始化／chunks載入完成 → wasm.search同步呼叫邊界未返回

D2約在request後220ms到達該邊界，完整操作約5.005秒逾時；沒有返回UTF-8 decode、JSON、JS results.map或自有mapping的start。尚未定位WASM內部演算法，單一高命中合成題不代表全部搜尋。

為什麼暫不追加8CPU／8GiB壓測？

5個查詢內樣本只覆蓋約0.216–4.235秒：4.019秒內4.041 CPU秒，約1.006核；quota throttling、memory max／OOM、回收／refault增量皆0。沒有支持單純加CPU quota或RAM的收益假說。更多worker的併發收益另議，不會自動由加大Pod取得。

82筆trace增加可觀察成本；最後記錄前81筆helper約111.688ms，末筆自身成本未知。診斷改了唯一一個JS，其他101570產物保持；不是未改引擎的效能A/B。

還有哪些舊問題未閉合？

原100頁中文「資料庫備份」Node1筆／browser3筆反例保留；本輪預定的歷史觀察因首題停止而未執行。正式query品質、consumer契約、ReBAC、中文接受、1M reader及長期維運仍未知。

05 · 何時才值得再投入？

先核對A的可重用程度及每站成本。只有Pagefind可能帶來足以抵銷adapter、worker、版本和升級回歸的淨省，且必要任務可接受，才選一個有界補驗。先前的上游／Rust/WASM內部研究建議已暫停；不因還能研究就繼續。

若未來找到受支持且不改必要語意的簡單調整，可重新提案；若主要依賴長期runtime／Rust／WASM fork，必須把維護責任先帶回團隊。這次trace是研究儀器，並非已決定的正式fork。
