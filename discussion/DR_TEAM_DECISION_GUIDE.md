# DR 架構選型：30 分鐘做出下一個決定

2026-11-17｜先讀[架構摘要](DR_ARCHITECTURE_DECISION.md)，需要追問再開[證據矩陣](DR_EVIDENCE_MATRIX.md)。

**會議產出是選一條路及責任人，不是建立更多實驗待辦。** 目標為最低增量長期維運、滿足真正的唯讀 DR 任務。現有證據支持討論有限試點，不是上線核准。

## 議程

| 時間 | 主持人帶入的具體材料 | 必須留下的決定 |
|---|---|---|
| 0–5分鐘 | 待命定期更新／Active凍結／驗證後切回；每日快照、一小時恢復僅工作假設 | 確認階段、凍結政策、RPO/RTO及不可妥協的Active可用性 |
| 5–10分鐘 | 一張C架構圖，對照完整A；固定Pod免去應用內熱切但仍有發布責任 | 現有A可重用什麼；C是否有明確擁有者 |
| 10–17分鐘 | N1/R0/C1三列證據，強調待命復原≠Active在線更新、C1 hold中止 | 哪個未知會真正改選，而非只是讓人更安心 |
| 17–25分鐘 | 下列四個選項及改選條件 | 選一項，最多指定一個下一步資訊需求或一個有界試點 |
| 25–30分鐘 | 填決策紀錄，逐項讀回 | owner、停止條件、下次日期／觸發事件；沒owner則不默認進行 |

## 帶著方案問，而非問「你們需要什麼」

| 對象 | 已有具體方案／證據 | 請做的選擇或提供的事實 |
|---|---|---|
| Product／內容使用者 | DR可title/body中英搜尋、Space／AND-tags與閱讀下載；排序不保證等同ES，highlight未列必須 | 指出3–5個一定要找到的文件情境。排序差異、沒有highlight、Active期間快照不更新，哪些可批准、哪些直接排除C？確認資料年齡與服務時間；不把待命重啟當Active停機核准 |
| API／Backend owner | 已測Web4＋API32＋read1＋download2的合成工作點，不是正式容量；exact total／tie已保留但成本不同 | 給既有request/response與流量範圍；精確total、排序、pagination、錯誤、retry、身份、限流哪些契約不可改？若必須原樣重用，A是否更省？ |
| Security／ReBAC／Backend | Space角色＋本地page/media關係；ReBAC備援是假設，snapshot可能舊 | 搬頁／撤權後舊快照如何處理？查不到授權如何拒絕？誰批准時差風險，哪些場景不能用提高同步頻率代替安全修正？ |
| 資料／備份 owner | 百萬index已測，但遠端正文僅256/257頁；PDF抽文可用 | 現有匯出是否覆蓋所有page/media／抽文？大小／數量及日更完成時間？提供現有清單即可，不要求先建新系統 |
| DR／Platform／DevOps | Active凍結、待命可考慮Recreate；本機拒壞／重裝有證據，完整中斷啟用尚未驗 | 若更新中遇災難，如何禁止promotion、停止現有更新者、找到異地良版並重啟導流？所需時間是否符合RTO？誰保留image／產物、確認主站可切回？先不選RollingUpdate或Recreate |
| 現有A維運 owner | A可沿用BE/DB/ES流程，但異地增量工時未知 | 展示一份現有IaC/runbook：部署、備份恢復、升級、容量警報、值班。已自動化與新增人工工作各是什麼？不要先估空泛人月 |
| C應用 owner | C需Rust binary／IPC／schema／manifest與release runbook | 是否有人願意負責升級、安全修補、builder失敗、worker crash、內容缺漏？若無owner，不以agent能快速寫程式代替長期責任 |

## 先確認最小復原提案

遠端manifest核准不等於已知可啟動；候選須在異地完成安裝與服務檢查才提交良版紀錄。保留良版全部產物與相容image，更新失敗不覆寫它。災難啟用先阻止／停止更新，再按良版pin重裝（若必要）、驗證及導流；ready但未提交仍選舊良版。Release／Storage／DR平台各有owner，提案未實作／未驗。

請團隊確認：能否沿用既有流水線單一寫入者及人工啟用runbook，安全避免promotion競爭？從沒有可用Pod到導流的成本是否符合RTO？凍結資料時，撤權與持續增加的資料年齡如何處理？主站部分恢復不能自動觸發failback。

在線熱切、dual-pool排空、只為Active刷新而做的跨版本路由／混載更新驗證移出最低範圍；Active故障復原與持續服務仍要負責。是否補長觀測由實際DR時間及資源風險決定，今天不自動開實驗。

## 四個可選結論

| 選項 | 適用條件 | 下一步與停止／改選條件 |
|---|---|---|
| **有限Tantivy試點** | 最低契約與owner明確；A重用不足以直接勝出；平台有良版啟用owner且同意凍結模型 | 限定一組代表資料／consumer與平台環境，先書面訂品質、權限、完整覆蓋、中斷待命更新時的良版啟用／RTO及Active資源驗收及時間預算。任一安全／完整性錯誤即停；不能在預算內滿足必要契約或無owner則回A／暫緩。會議批准前不開新研究里程碑 |
| **只取得一項關鍵事實** | 如A已有完整異地自動化、或consumer硬性契約尚不明，答案能反轉選擇 | 指定資料持有人、交付物、期限及兩種答案分別如何選；不把所有未知都變成待辦 |
| **重用A** | 既有流程增量低、需要高度相容、或C維護責任無人承擔 | 沿現有DR交付流程確認異地恢復與權限；不是聲稱A不用驗證，也不以本研究的獨立ES測試代替完整A驗收 |
| **暫緩** | 需求／責任／預算未明，或沒有迫切採用理由 | 記錄觸發條件（例如新的DR要求、指定owner、取得必要資料）；停止新增實驗直到條件改變 |

## 決策紀錄模板

| 欄位 | 會議填寫 |
|---|---|
| 決策日期／決策人 | 待填；角色與個人皆需確認 |
| 所選方案 | 有限C試點／補一項事實／A／暫緩 |
| 必要任務與成功條件 | 使用者與consumer可完成什麼；服務範圍及SLO |
| 明確接受的降級及批准者 | 搜尋差異、Active凍結／資料年齡、待命重啟、實際會遇到的409體驗分開；未填不視為接受Active停機 |
| 不可妥協的正確性 | 未授權拒絕；可信page/media關係；不混錯版本；應備份內容不缺漏 |
| 支持證據與範圍 | N1／R0公開來源；C1敘述公開、原始資料本機未公開；不能合併成全鏈通過 |
| 最多一項決策關鍵未知 | 什麼答案會改選？誰已有答案？ |
| 試點gate／停止條件／時間預算 | 中斷待命更新時良版可復原、啟用RTO、Active容量與真實權限／品質／完整覆蓋；未設定則試點不開始 |
| 責任人 | Product、API、Security、Platform、A與C維運各誰負責 |
| 下一個日期或觸發事件 | 具體填寫，不預設無限探索 |
